# P9 非记忆、非欢愉角色共享机制收口计划

本文面向没有前序会话上下文的规划、执行和验收线程。P9 的目标不是逐个手写角色，而是
将当前 79 条非记忆、非欢愉已发布角色共同依赖的来源接线、能力图执行语言和战斗领域语义
补成通用内核，再用全目录审计确认每张角色卡只组合这些共享机制。

现行范围、节点分类和机制包归属以以下文档为准：

```text
docs/character_execution_cards/CHARACTER_ABILITY_SCOPE_CLASSIFICATION.md
docs/character_execution_cards/CHARACTER_SHARED_MECHANISM_GAP_PLAN.md
```

P9 不重新扫描或讨论记忆、欢愉的专属语义。两条新命途只是延期，未来应复用 P9 已建立的
共享机制，只为真正新增的 owned-combatant 或命途规则建立增量计划。

## 1. 使用方式

本文只维护 P9 总目标、全局边界、阶段依赖和最后一节的唯一阶段 checklist。每个阶段的
详细目标、负例、拟改范围和验证预算分别保存在：

```text
docs/p9_execution_cards/
```

执行线程一次只读取 `README.md`、当前执行卡及卡内明确列出的直接依赖。不得通读后续卡，
不得按本文阶段摘要自行扩大实现，也不得自动进入下一阶段。实际代码事实若使当前卡目标或
验收失效，必须停止并交回规划线程修订。

执行线程只能提交 `ready_for_review`，不能修改本文 checklist、不能提交 Git、不能把部分
来源通过称为阶段完成。验收线程检查生产代码、来源、调用链、失败原子性和 evidence 后，
才允许勾选阶段并建立检查点。

P9 的 `ready_for_review` 必须同时满足三项门槛：本卡禁止的非法状态已经在生产构造或提交
边界不可表示；本次改变的公开契约已核对全部正式调用者且不存在旧语义残留；全部已知
blocked/deferred/source gap 已按原因和后续 owner 聚合，并为每组保留一个可反查 raw 的代表
来源。聚焦验证只为每条生产不变量保留一个最小反例，不得以扩大验证矩阵替代内核约束。
任一门槛没有证据时，执行状态只能是 `blocked`、`plan_mismatch` 或 `context_gap`。

原 P9-S5 同时跨越目标 IR、实体关系、动作交互和共享 RNG 四个架构边界，已经拆为严格
串行的 S5A-S5D2。旧单卡不再是执行入口；S5D 又按“随机基础契约”和“动作接线/聚合”
拆为 S5D1、S5D2。全部子卡验收后才视为原 S5 目标完成。

原 P9-S6 又把来源责任分区与 committed-state evaluator 混在同一卡内，已经拆为 S6A、S6B。
S6A 固定完整条件分母、非战斗排除和后续 owner；S6B 只消费该契约实现求值。

## 2. 前因后果

P1-P8 已建立战斗状态、状态生命周期、伤害、时间线、队列、召唤、数据卡、公式、构筑、
装备和 replay 等底座。当前 79 条目标角色都能生成正式基础战斗单位，但角色完整能力仍有
以下共同断点：

- 共享角色运行时来源没有统一接入角色能力图。
- 17 条记录共有 19 个动作阶段或入口绑定缺口。
- 行迹、星魂的静态贡献和动态能力图尚未通过一条通用构筑绑定链消费。
- 动态值、目标、条件、控制流和事件回调仍只接纳部分真实角色来源形状。
- 状态、伤害、资源、队列、死亡、击破、形态和独立行动实体的底座存在，但角色来源的
  payload、事件生产者和生命周期尚未全部接通。
- 6 个混淆战斗节点族共 110 次出现，另有大黑塔追加攻击分支引用的真实 ability 缺失。

旧盘点中的 blocked 数量混合了表现节点、上游事件准入和下游效果语义。同一状态任务因
多个事件未准入会重复报数，不能按 blocked 总数或角色数估算工程量。P9 按共享根因施工，
每个来源出现只能有一个当前主要责任阶段和必要的下游依赖。

## 3. 目标架构

P9 完成后，角色内容应沿唯一链路进入战斗：

```text
角色主能力 / 共享角色能力 / 行迹 / 星魂
                  |
                  v
      范围分类与来源图 -> Canonical IR
                  |
                  v
       CharacterBuildAssembler
                  |
                  v
  已装配能力引用 + 正式动作定义 + 初始状态
                  |
                  v
 数值/目标/条件/控制流/事件 -> 通用领域系统 -> 原子提交
                  |
                  v
       settlement / source audit / replay
```

角色卡只保存来源组合和动作定义。构筑装配器只解析最终等级、行迹、星魂和机制引用。
runtime 只执行类型化 IR，不读取 raw、角色名、技能名、文本或 source trace 决定规则。

## 4. P9 总目标

P9 要得到以下结果：

- 79 份角色主能力和 1 份共享角色能力形成完整、可指纹化、范围诚实的来源目录。
- 表现、客户端、AI 和统计分支从 gameplay admission 退役；携带战斗事实的 UI/输入节点先
  投影成特殊资源、目标持续性、拓扑或环境契约。
- 动作、强化阶段、被动入口、独立 ability、行迹和星魂都唯一绑定真实来源。
- 最终构筑选择在装配阶段解析；runtime 不判断养成过程，也不重复应用默认节点。
- 当前来源中的动态值、目标、条件、控制流和战斗随机形状都由通用执行语言表达。
- 普通动作、状态回调和战斗事件复用同一效果契约，不存在 callback 专用第二套 handler。
- 125 个战斗事件族按真实生产者归入动作、状态、结算、资源、队列、单位、波次等生命周期，
  并通过稳定身份、typed payload 和原子派发执行。
- 状态、伤害、治疗、护盾、资源、技能可用性、行动轴、死亡、击破、形态和独立行动实体
  的角色来源形状全部接入现有通用领域系统。
- 所有 gameplay RNG 经过同一确定性 ledger，表现随机不消费推演随机流。
- 当前 6 个混淆族得到可靠解码和归属；确实无法从来源证明的项保持 source gap，不猜测。
- 全目录重新计算后，`lowering_gap`、`admission_gap`、`implementation_missing` 和
  `validation_gap` 为零；真实 source gap 单列且阻止受影响角色被宣称完整可玩。
- 代表纵切由当前未证明来源形状动态选择，不预设人数；纵切不能替代 79 条目录审计。

## 5. P9 明确不做

- 不处理记忆命途 7 条记录和欢愉命途 6 条记录的专属机制。
- 不模拟角色获取、等级材料、晋阶材料、行迹解锁路线、星魂取得和技能升级过程。
- 不实现动画、镜头、音效、VFX、HUD、客户端选目标流程或物理弹道。
- 不实现敌方 AI 或自动战斗。外部推演器像玩家一样查询并选择敌我动作。
- 不按角色名、技能名、固定 ID、固定文件名、文本描述或观测伤害建立 runtime 分支。
- 不重做 P2/P7/P8 已验收底座；只有当前角色真实来源暴露共享缺口时做最小通用扩展。
- 不借 P9 建立全项目 validator registry、持久验证缓存或第二套场景/结算实现。
- 不把真实 source gap 改名为实现完成，也不为通过目录审计伪造 synthetic gameplay 来源。

## 6. 全局架构红线

1. raw TBGD 只进入 discovery/compiler/lowering；runtime 只读 Canonical IR 和正式构筑。
2. 每个 mutation 必须来自真实 IR 节点，并原生生成 settlement、来源审计和 replay。
3. 缺来源、目标、参数、事件上下文或公式时，在提交前 blocked，state、event 和 RNG 不变。
4. 同一效果语义只有一个生产入口；动作、callback、provider 和战斗事件不得复制 handler。
5. 构筑条件在 assembly 解析，事件条件在 typed event context 解析，两者不得混用。
6. 空目标集合、合法无召唤关系和解析失败必须是不同状态。
7. 事件身份由生产者和生命周期定义；同身份不同 payload 或来源必须 fail-closed。
8. 外部推演器只提交内核公布的动作、目标和 RNG 选择，不计算合法性或效果。
9. 固定角色 ID 只允许出现在明确标记的最终示例 manifest，不能进入通用验证选样或生产代码。
10. 当前阶段没有真实生产者但依赖未来新命途/怪物/关卡的机制，只能记录外部内容依赖，
    不能用合成生产者冒充已闭合。

## 9. 严格依赖图

P9 默认严格串行，不使用并行 worktree。原因是 S0-S17 持续修改相同的 lowering、IR、
evaluator、event 和 runtime 共享边界，并行合并会增加遗漏和重复实现风险。

```text
S0 -> S1 -> S2 -> S3 -> S4 -> S5A -> S5B -> S5C1 -> S5C2 -> S5D1 -> S5D2 -> S6A -> S6B -> S7 -> S8 -> S9
 -> S10 -> S11 -> S12 -> S13 -> S14 -> S15 -> S16 -> S17
 -> S18 -> S19 -> S20
```

每个阶段必须基于前一阶段的已验收 Git 检查点。S3 可以把已解码来源重新分配给 S4-S17，
但不能在 S3 提前执行下游领域语义。S18-S20 默认不修生产机制：发现 gap 时退回责任阶段，
修复并形成新检查点后再重新进入审计。

## 10. 验证与资源总策略

P9 严格遵守 `docs/AGENT_WORKFLOW_AND_VALIDATION.md`：

- 每阶段一个权威业务主入口和一份 summary。
- 默认只运行 `compileall + 当前主验证 + git diff --check`，direct 由实际修改调用链触发，
  最多两个。
- family 和角色过滤必须在来源读取、IR/RuleBook 构建和 evidence 生成前生效。
- S0 建立的角色能力窄投影是生产 compiler API，不是验证缓存；后续阶段复用它，不构建
  完整 Canonical IR 后再过滤。
- 完整主入口最多一次诊断和一次最终运行；中间修复只跑失败 family/矩阵行。
- 不写完整 Canonical IR、RuleBook、raw ability 或全 transition dump。
- 不重跑 P1-P8 聚合、`validate_v0_209` 或已经冻结的阶段验证套餐。
- 旧验证只有在生产调用链实际触达且谓词仍有效时，抽取最小 direct；不修改生产代码迎合
  过时假设。

## 11. Gap 和完成口径

每个来源项只允许以下状态：

- `executable`：来源、lowering、admission、runtime、settlement、audit、replay 闭合。
- `non_gameplay`：完整分支证明不改变战斗，零 mutation/event/gameplay RNG。
- `source_gap_blocked`：当前 raw 确实缺少或无法唯一证明所需来源，受影响角色不能正式准入。
- `lowering_gap`：来源存在但 IR 不完整，必须回责任阶段修复。
- `admission_gap`：IR 存在但未进入正式执行，必须修复。
- `implementation_missing`：来源已准入但通用 runtime 无法执行，必须修复。
- `validation_gap`：生产可能正确但证据不成立，必须修正证据或生产入口。
- `external_content_dependency`：通用消费者存在，但当前阶段没有记忆/欢愉/怪物/关卡真实生产者；
  不计为 79 条角色通过，也不误报为共享内核失败。

P9 使用两个明确结论，禁止混淆：

1. `P9-SHARED-MECHANISMS-DONE`：79 条范围内四类内部 gap 为零，通用机制和审计完成；
   允许存在已证明的真实 source gap，但必须列出受影响角色。
2. `current_79_character_catalog_all_executable`：只有真实 source gap 也为零，且 79 条角色的
   全技能、全行迹、全星魂全部正式准入时才为 true。

因此 P9 可以在共享内核已完成但个别 raw 真缺源时形成机制检查点，但不得对用户宣称
“79 名角色全部制作完成”。
