# P6 架构边界回正重构任务计划

本文档面向一个没有前文上下文的新执行线程。P6 的任务不是新增大功能，而是把 P1-P5 过程中逐步暴露出来的职责偏移拉回到新的架构边界上。

P6 的背景是：v8 已经完成 P1 最小战斗纵切、P2 状态底座、P3 召唤物 / servant 底座、P4 角色卡 / 怪物卡数据卡扩面、P5 公式 / 动态值 / 参数绑定通用准入。随后项目明确了长期三层结构：

```text
UI / 推演器 / CLI：只查询、选择、提交、展示
角色卡 / 怪物卡 / 装备 / 关卡：声明具体内容拥有哪些通用机制
战斗内核：执行通用机制，产出状态变化、结算、审计和 replay
```

当前代码并不是整体推倒重来，但存在几类越界倾向：

- 战斗结算有时会顺着“这条结果来自哪里”的审计信息回头找公式或参数。
- 召唤物和召唤怪生成时，运行时系统知道了过多角色卡 / 怪物卡装配细节。
- 场景构建、波次、召唤系统里存在重复读取怪物资料并拼装战斗单位的逻辑。
- 内容卡和内核之间缺少更硬的访问边界，后续全角色 / 全怪物扩面时容易把专属规则写进错误层。

P6 的目标是先回正这些边界，再继续做角色、怪物、装备、关卡的大规模内容扩面。

## 使用方式

本文档只有第 15 节是唯一可打标 checklist。其他章节是阶段说明、边界和验收参考，不是并行清单。

执行线程必须一次只执行一个 P6-Sx 阶段。每个阶段开始前必须先提交阶段执行卡，并等待规划 / 验收线程确认后才能改文件。

执行线程最多只能提交 `ready_for_review`，不能自称 `done`，不能修改第 15 节 checklist，不能把 `[ ]` 改成 `[x]`。阶段完成标记只能由验收线程在复核真实代码、真实验证输出、summary / matrix、审计 evidence 后更新。

P6 是重构阶段，`ok=true` 不是完成证明。验收时必须说明：

- 哪些越界路径已经消失。
- 哪些路径只是审计字段保留，不参与规则执行。
- 哪些旧路径暂时保留，为什么不影响当前阶段边界。
- 哪些验证只证明回归不破坏，哪些验证真正证明边界收紧。

资源控制要求沿用 P4/P5 口径。默认只跑本阶段最小验证和直接回归；涉及 P1-P5 聚合验证时必须串行、低优先级、输出到 `/tmp`，禁止并行重验证和默认写大产物。

## 0. 总目标

P6 完成后，v8 应达到以下状态：

- 战斗内核结算伤害、削韧、资源、状态数值时，不再靠审计来源信息回头挖规则。
- 召唤物、servant、召唤怪和波次生成单位时，运行时只执行提前准备好的“出生单”，不负责理解内容卡内部结构。
- 角色卡 / 怪物卡只声明机制组合，不自己执行伤害、状态、队列、目标、资源或行动条。
- 场景构建层只装配初始状态，不推导战斗规则。
- RuleBook 仍可作为集中索引，但 runtime consumer 只能通过稳定机制视图读取结算所需内容。
- 新增架构审计验证，防止后续代码再次出现同类越界。

## 1. P6 不做什么

P6 明确不做：

- 不批量制作全角色卡。
- 不批量制作全怪物卡。
- 不实现完整光锥、遗器、套装、关卡环境。
- 不实现外部推演器。
- 不重做 UI。
- 不把旧 v7、旧 model pack、观测伤害、技能文本或固定答案接入 runtime。
- 不为了通过验证构造假正例。
- 不把所有 `source_trace` 字段删除；审计和 replay 仍然需要来源信息。P6 只禁止把来源信息当成规则入口。

## 2. 当前已知偏移点

### 2.1 结算层顺着来源信息找规则

当前伤害和削韧相关路径中，存在“先拿到来源，再从来源里找公式或数值绑定”的流程。这个方向不干净。

目标形态应该是：在 lowering 或数据卡装配阶段，就把一次伤害、一次削韧、一次资源变化需要的计算说明放到稳定机制记录里。runtime 只读这份计算说明执行；来源信息只随结果一起进入审计。

### 2.2 召唤系统过度理解内容卡

当前召唤系统在计划和应用召唤时，会读取怪物资料、战斗面板、怪物卡来源、servant 动作、生命周期等信息。这让“内容装配”和“机制执行”混在一起。

目标形态应该是：角色卡或怪物卡先准备一张“出生单”。这张出生单写清楚召唤出来的是谁、归属谁、初始位置、初始行动状态、生命周期、动作来源、清理策略。runtime 只照单生成单位和记录结算。

### 2.3 波次和场景构建存在重复装配逻辑

场景构建和波次系统也会读取怪物资料并拼装战斗单位。部分读取是合理的初始装配，部分则可能和召唤系统重复。

目标形态应该是：所有“生成一个战斗单位”的路径共享同一种出生单。区别只在来源是初始配置、波次、角色召唤、怪物召唤，不能每个系统各自拼一套单位。

### 2.4 内容卡和内核边界还不够硬

内容卡可以声明“我有什么技能、什么状态监听、什么召唤入口、什么特殊资源”，但不能自己执行机制。内核也不能按角色名、怪物名、技能名、固定 ID 或内容卡私有字段分支。

P6 需要把这条边界变成可检查的结构，而不是只靠人工约定。

## 3. 阶段总览

```text
P6-S0  找出所有“谁在错误地替谁做事”的代码路径，并给每条路径定性
P6-S1  让伤害 / 削韧结算改为拿明确计算单执行，不再从审计来源里倒查规则
P6-S2  让召唤物 / servant 生成改为照出生单执行，不再由召唤系统临时拼单位
P6-S3  让初始配置、波次刷怪、怪物召唤怪共用生成单位流程，避免三套拼装逻辑
P6-S4  检查内容卡是否偷做内核结算、内核是否偷写内容特判，并把能回正的回正
P6-S5  给 RuleBook 和静态检查加边界防线，防止以后继续越界读取
P6-S6  串起 P6 回归、报告和剩余问题归属，证明回正没有破坏 P1-P5
```

## 4. 阶段执行卡要求

每个阶段开始前，执行线程必须先提交阶段执行卡：

```text
阶段：
阶段目标：
  - 本阶段完成后，系统应新增或改变哪些具体能力。
  - 本阶段要消除哪几类具体错误职责。
  - 本阶段不追求哪些看似相关但实际属于后续阶段的结果。
本阶段只改哪些文件：
本阶段禁止改哪些文件：
将新增 / 修改哪些类型、函数、脚本或报告：
验收标准：
  - 每条标准必须能用代码位置、验证输出、summary/matrix 或报告 evidence 证明。
  - 每条标准必须写清楚“做到什么才算通过”。
  - 每条标准必须写清楚“出现什么情况就不能通过”。
验收证据映射：
  - 哪个改动对应哪个验收标准。
  - 哪个验证对应哪个验收标准。
  - 哪个报告字段或样例对应哪个验收标准。
哪些情况必须判定为 blocked / gap / deferred：
要跑哪些验证，为什么足够：
哪些验证本阶段明确不跑，原因是什么：
预计资源风险和限峰值措施：
完成后提交哪些 evidence：
```

阶段执行卡必须是具体执行设计，不能复述本文档。目标和验收是执行卡里最重要的部分，禁止用一句话概括。比如 P6-S2 不能只写“做出生单”，必须写清楚：

- 完成后召唤系统会少做哪些事。
- 哪些召唤路径会改为消费出生单。
- 出生单至少要包含哪些生成单位必需信息。
- 哪些旧读取只允许保留为审计信息。
- 哪些负例证明缺出生单时不会生成单位。
- 哪些 P3 既有能力必须保持不退化。

阶段执行卡里禁止只写抽象词。例如“审计越界路径”“收紧边界”“优化契约”都不够。必须写成能落地检查的话，例如“搜索伤害结算里是否存在从审计来源倒查倍率的代码”“检查召唤系统是否还在读取怪物卡并拼单位”“检查配置层是否自己算行动条或技能可用性”。

如果执行卡的目标只描述“要做什么动作”，没有描述“系统完成后应变成什么样”；或者验收只写“验证通过”，没有说明验证证明了哪条目标，则执行卡不能通过确认。

## 5. P6-S0 架构越界总账本

### 目标

建立 P6 总账本。S0 的目标不是改代码，而是把当前所有“职责可能放错层”的代码路径找出来，并说清楚每条路径后续该不该改、在哪一阶段改。

S0 要回答的不是“哪些地方出现了某个字段名”，而是下面五个具体问题：

1. 战斗结算时，有没有代码拿“这条结果来自哪里”的审计信息，回头寻找伤害倍率、削韧数值、资源数值或状态数值。
2. 召唤物、servant、怪物召唤怪、波次刷怪生成单位时，有没有代码临时读取怪物资料、角色卡、怪物卡、动作列表、生命周期策略，然后自己拼出一个战斗单位。
3. 初始配置和场景构建有没有越过“装配初始状态”的职责，自己计算技能可用性、目标范围、行动条、资源、状态结算或召唤物行为。
4. 内容卡里有没有直接执行伤害、状态、队列、资源、目标、行动条等内核机制；内核里有没有按具体角色、怪物、技能或固定 ID 写分支。
5. 缺资料、缺来源、缺目标、缺计算说明时，有没有代码用默认值继续执行，而不是 blocked / state unchanged。

### 本阶段只做

- 搜索并阅读以下五类代码现象，只做分类和留档：
  - “从审计来源倒查规则”：例如函数名或逻辑里出现 `from_trace`，或者从来源记录里递归找公式、倍率、数值来源。
  - “运行时拼战斗单位”：例如召唤、波次、配置构建过程中读取怪物资料、角色卡 / 怪物卡、动作列表、生命周期，再创建单位。
  - “配置层推导规则”：例如场景构建、UI 工作台、scenario helper 自己计算技能是否能用、目标范围、行动顺序、战技点、能量、状态变化。
  - “内容特判”：例如 core / systems 中按具体角色、怪物、技能名、固定 ID、固定文件名分支。
  - “缺口默认执行”：例如缺来源、缺计算说明、缺目标、缺资料时仍用默认倍率、默认削韧、默认目标、默认行动状态继续执行。
- 按路径分类：
  - `audit_only`：只用于审计、报告、replay，可以保留。
  - `rule_input_violation`：来源信息被用来找规则或参数，需要重构。
  - `content_assembly_in_runtime`：runtime 负责了内容装配，需要重构。
  - `scenario_assembly_ok`：场景构建阶段合理装配初始状态。
  - `scenario_rule_violation`：场景 / UI / helper 自己推导了战斗规则，需要回正。
  - `content_execution_violation`：内容卡或内容 helper 自己执行了内核机制，需要回正。
  - `core_content_special_case`：内核按具体内容写了特判，需要回正。
  - `fallback_execution_violation`：缺资料时仍默认执行，需要回正。
  - `unclear`：当前无法判断，必须写明需要人工决策的问题。
- 输出轻量 summary 和 matrix，不写大产物。

### 本阶段不做

- 不改 runtime 行为。
- 不搬迁召唤逻辑。
- 不修改公式绑定。
- 不清理所有来源字段。

### 阶段通过口径

- 五个具体问题都被检查过，不能只检查伤害或只检查召唤。
- 每条可疑路径都有文件位置、当前行为、为什么可能越界、分类、后续归属阶段。
- `unclear` 必须有明确问题说明，不能被当成完成项。
- 不能把“出现了来源字段”直接等同于越界；必须区分审计字段和规则输入。
- 不能把“验证目前通过”当成边界正确。
- S0 结束时必须能直接指导 S1-S5：哪些路径进入伤害 / 削韧回正，哪些路径进入召唤出生单，哪些路径进入波次 / 配置生成单位，哪些路径进入内容卡边界，哪些路径进入静态防线。

### 最小验证

- `git diff --check`
- 本阶段新增的轻量审计脚本或报告生成命令。
- 不跑 P1-P5 聚合，因为本阶段不改行为。

## 6. P6-S1 伤害 / 削韧结算入口回正

### 目标

让伤害和削韧结算在执行前就拿到“这次怎么计算”的明确说明。执行时不能再根据“这次结果来自哪里”的审计信息倒查倍率或数值。

### 本阶段只做

- 处理 S0 中归到伤害 / 削韧的 `rule_input_violation`。
- 找出伤害、削韧当前从审计来源中挖公式、倍率、参数、数值来源的路径。
- 在对应 IR / plan / consumer contract 中补上稳定计算入口。
- 让 runtime 只读取稳定计算入口执行。
- 来源信息继续进入 settlement、source audit、replay，但不能参与公式选择。
- 缺计算入口时必须 blocked 或 process-only，不能 fallback 到默认倍率或默认削韧。

### 本阶段不做

- 不重写完整伤害系统。
- 不扩展所有复杂公式。
- 不处理召唤物生成。
- 不批量解释角色或怪物技能。

### 阶段通过口径

- 伤害和削韧主路径不再通过审计来源信息寻找计算规则。
- 至少各有一个真实来源正例证明新入口可执行。
- 至少各有一个负例证明缺计算入口时不会产生假 mutation。
- settlement、source audit、replay 仍能追溯到真实来源。

### 最小验证

- `compileall`
- 本阶段新增或修改的伤害 / 削韧验证。
- 与 P1 伤害、P5 数值绑定直接相关的回归。
- `git diff --check`

P1-P5 聚合只在本阶段改到共享 action execution、damage reducer、snapshot / replay 或 source audit 时串行运行。

## 7. P6-S2 召唤物 / servant 出生单回正

### 目标

让召唤物、servant、忆灵类单位在进入 runtime 前就准备好“出生单”。runtime 只照单生成单位、记录归属关系、进入时间线和生命周期，不再临时理解角色卡或怪物卡。

### 本阶段只做

- 处理 S0 中归到召唤物 / servant 的 `content_assembly_in_runtime`。
- 设计或复用一份通用出生单，覆盖：
  - 生成谁。
  - 归属谁。
  - 是否在场上。
  - 初始位置或后场关系。
  - 初始行动状态。
  - 生命周期和清理策略。
  - 可行动入口。
  - 来源和审计证据。
- 让召唤物 / servant 生成路径消费出生单。
- 缺出生单、出生单不完整、来源不准入时，生成必须 blocked 且 state unchanged。
- 保留 P3 所需的 source audit、replay、owner / summoner relation。

### 本阶段不做

- 不补全所有忆灵和全角色召唤物。
- 不做全怪物召唤技能。
- 不改变推演器接口。
- 不把角色专属召唤规则写进 summon runtime。

### 阶段通过口径

- 召唤 runtime 不再自己理解怪物卡或 servant 卡的内部装配细节。
- 现有 P3 召唤物 / servant 正例仍通过。
- 缺出生单负例不会生成单位。
- 出生单中的来源仍能追溯到数据卡或 Canonical IR。

### 最小验证

- `compileall`
- P3 召唤物 / servant 直接验证。
- 本阶段新增出生单正例和负例验证。
- `git diff --check`

P1/P2/P4/P5 聚合不默认运行；只有改到共享 source audit、snapshot/replay 或 data-card contract 时再串行运行相关聚合。

## 8. P6-S3 波次 / 初始配置生成单位回正

### 目标

让“战斗开始放入敌人”“换波次刷出敌人”“怪物召唤怪物”都使用同一种生成单位流程。配置层和波次层可以决定什么时候生成谁，但不能各自拼一套战斗单位规则。

### 本阶段只做

- 处理 S0 中归到波次 / 初始配置 / 怪物召唤怪的 `content_assembly_in_runtime` 和 `scenario_rule_violation`。
- 审计场景构建和波次系统中生成战斗单位的路径。
- 区分合理的初始装配和 runtime 越界装配。
- 将波次刷怪和怪物召唤怪接入通用出生单。
- 初始配置可以继续负责装配 battle setup，但不能推导战斗规则。
- 缺怪物资料、缺出生单、缺来源时必须 blocked，不生成半成品单位。

### 本阶段不做

- 不实现完整波次系统扩面。
- 不制作全怪物阶段切换。
- 不做关卡环境机制。
- 不让配置层计算技能可用性、行动条或状态结算。

### 阶段通过口径

- 初始配置、波次、召唤生成单位的差异来自来源和触发时机，不来自三套互相不兼容的拼装逻辑。
- 波次 / 召唤相关 source audit 和 replay 不退化。
- 缺资料负例不会生成单位。

### 最小验证

- `compileall`
- P3 召唤验证中涉及召唤怪的部分。
- 当前 wave / battle setup 直接验证。
- `git diff --check`

如触达 P4 怪物卡 contract，必须串行运行 P4 聚合或其直接子验证。

## 9. P6-S4 内容卡机制声明边界审计与收紧

### 目标

确认角色卡、怪物卡和召唤物子卡只是在说“我有什么机制”，没有自己做结算；同时确认 core 没有写“某个具体角色 / 怪物 / 技能例外处理”。

### 本阶段只做

- 处理 S0 中归到 `content_execution_violation` 和 `core_content_special_case` 的路径。
- 审计角色卡、怪物卡、怪物技能、状态 callback、资源、队列、行动可用性路径。
- 找出内容卡中疑似直接执行机制的位置。
- 找出 core 中疑似按具体内容分支的位置。
- 将能立刻回正的小范围路径改为通用机制声明。
- 对暂时不能回正的路径记录为 backlog，并说明需要扩展哪类通用机制。

### 本阶段不做

- 不批量重写角色卡。
- 不补全全怪物被动。
- 不把无法表达的专属机制强塞到现有机制里。
- 不为了清除特判而删除已有可执行机制。

### 阶段通过口径

- 内容卡直接执行机制的路径有明确清单和处理结果。
- core 按具体角色 / 怪物 / 技能特判的路径有明确清单和处理结果。
- 已回正路径有正例和负例。
- 未回正路径不能被标成完成，必须进入后续 backlog。

### 最小验证

- `compileall`
- 本阶段触达系统的直接验证。
- 与状态、队列、资源、行动可用性相关的最小回归。
- `git diff --check`

不默认跑全量 P1-P5；触达共享 reducer 或 source audit 时才扩大。

## 10. P6-S5 RuleBook 访问边界与静态防线

### 目标

保留 RuleBook 作为资料索引，但给运行时加更窄的读取入口和静态检查，让后续代码更难再次从错误层读取规则。

### 本阶段只做

- 处理 S0 中归到 `fallback_execution_violation`，以及 S1-S4 后仍需要静态防线约束的路径。
- 梳理 runtime 目前通过 RuleBook 读取哪些内容。
- 区分机制执行视图、内容装配视图、审计视图。
- 对高风险读取加更窄的 accessor 或 boundary helper。
- 新增轻量静态检查，至少覆盖：
  - runtime 不能读取 raw TBGD。
  - runtime 不能读取 TextMap。
  - runtime 不能从审计来源信息里反查规则。
  - UI / 推演器 / scenario 不能写入已推导规则结果。
- 静态检查必须以结构化文件范围和函数名为准，不能靠固定单个样例。

### 本阶段不做

- 不强行拆分整个 RuleBook 类。
- 不重命名大量字段。
- 不删除 source audit 所需字段。
- 不把静态检查写成高负载全量数据库扫描。

### 阶段通过口径

- RuleBook 仍能服务现有验证。
- runtime 访问边界更窄，新增越界路径能被静态检查发现。
- 静态检查误报可解释，不能为了消除误报把检查写宽到无效。

### 最小验证

- `compileall`
- 新增静态边界检查。
- P1/P2/P3/P4/P5 中与被改 accessor 直接相关的最小回归。
- `git diff --check`

## 11. P6-S6 回归验证、报告和 P6 聚合验收

### 目标

证明 P6 已经把主要职责偏移拉回正确层级，并且没有破坏 P1-P5 已验收能力；剩余不能本轮解决的问题必须明确归属后续阶段。

### 本阶段只做

- 新增或更新 P6 聚合验证。
- 继承 S0-S5 的所有 unresolved / backlog，不允许聚合脚本覆盖分阶段 gap。
- 串行运行必要 P1-P5 回归。
- 输出 P6 验收报告。
- 更新交接文档和文档索引。

### 本阶段不做

- 不新增新机制。
- 不补全 backlog。
- 不把 P6 未解决项改名为完成。

### 阶段通过口径

- P6 聚合能证明主要架构边界已回正。
- P1-P5 当前应通过的聚合仍通过。
- 当前不要求全正例完成的阶段，仍按原口径保留 gap。
- P6 剩余 backlog 有明确后续阶段归属。

### 最小验证

- `compileall`
- P6 聚合验证。
- P1/P2/P3/P4/P5 聚合，串行、低优先级、输出到 `/tmp`。
- 静态边界检查。
- `git diff --check`

## 12. 验收总口径

P6 只能按“边界回正”验收，不能按“新功能覆盖率”验收。

允许通过的情况：

- 现有可执行机制仍可执行。
- 以前靠越界路径执行的机制，已改为明确机制合同。
- 暂时缺合同的路径 blocked 或留为 backlog，不产生假 mutation。
- 审计来源仍完整，但不再作为 runtime 找规则的入口。
- 召唤、波次、初始配置生成单位的职责更统一。

不允许通过的情况：

- 把来源信息字段删掉导致 source audit / replay 退化。
- 把内容卡执行机制伪装成“声明机制”。
- 让 runtime 按角色名、怪物名、技能名、固定 ID 或文件名分支。
- 用默认倍率、默认削韧、默认目标、默认行动条补过缺口。
- 聚合脚本显示 `ok=true`，但分阶段仍有未解释越界路径。

## 13. 验证范围分层

### 必跑最小集

每个阶段必须运行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m compileall -q simulator_v8_clean_core simulator_v8_ui
git diff --check
```

如果本阶段只生成报告且不改 Python 代码，可以只运行 `git diff --check` 和本阶段报告脚本；但 ready_for_review 必须说明为什么不跑 compileall。

### 直接回归集

按触达范围选择：

- 改伤害 / 削韧：跑 P1 伤害相关、P5 数值绑定相关验证。
- 改召唤 / servant：跑 P3 召唤物 / servant 验证。
- 改波次 / 初始配置：跑 battle setup / wave 直接验证，必要时跑 P4。
- 改状态 / 队列 / callback：跑 P2 状态、P1 队列相关验证。
- 改 source audit / replay / mutation：扩大到 P1-P5 聚合。

### 全量聚合集

只有以下情况运行 P1-P5 全部聚合：

- S6 聚合验收。
- 改到共享 reducer、snapshot、replay、source audit、RuleBook 核心索引。
- 验收线程明确要求。

全量聚合必须串行运行，不和其他重验证并行。
