# 可移植的 Agent 执行与验证流程

Status: **standalone reusable template**

这是一套可复制到其他代码仓库的轻量流程。它优化的是在有限时间和 token 下的**预期工程损失**，不是
追求零缺陷、最多测试或最多审计。目标是阻止重大、可达、难回退的问题，并以合理成本减少普通缺陷。

默认先只复制本文件。项目稳定后，再按附录把执行卡和问题登记拆成独立文件。带 `<...>` 的内容需要由
目标项目填写；项目自己的架构、命令和门禁始终优先于这里的示例。

## 1. 核心原则

1. **事实先于计划**：当前代码、测试和本地 Git 是实现事实；架构和计划文档是意图事实。冲突时先核实，
   不在假事实上继续施工。
2. **最小充分流程**：按风险选择 `LIGHT`、`STANDARD` 或 `STRICT`，不让流程成本接近或超过实现收益。
3. **先纵切、后铺开**：按“一个不变量 -> 一个有用反例 -> 生产实现 -> fast”尽早取得真实反馈。
4. **模型升级不扩权**：提高 reasoning 或换模型只能增加认知能力，不能增加范围、依赖、权限或写路径。
5. **验证观察行为**：只运行能观察本次变更的门禁；失败后只复跑失败项及直接受影响项。
6. **审计稀疏且有界**：外部审计只用于高风险能力激活点，不能变成每个小步骤的验收仪式。
7. **稳定后一次提交**：验证和审计收敛前不反复提交 `fix`；最后用一个提交绑定稳定候选。
8. **按模式学习**：只记录重复或高影响的流程问题，不把普通修错写成流水账。

完成标准不是“找不到任何问题”，而是：约定边界和证据完成，且没有未处理的重大可达风险。

## 2. 最小项目配置

开工前只需明确以下内容：

| 配置 | 项目需要回答的问题 |
|---|---|
| 事实入口 | 代理首先读取哪个根提示词/事实索引？ |
| 产品权威 | 架构、路线图、计划发生冲突时谁优先？ |
| 当前卡 | 本轮唯一生产结果、正式调用者和非目标是什么？ |
| 写集合 | 哪些路径允许修改，哪些用户改动必须保护？ |
| 本地门禁 | 本项目的 format、lint、type、test、build 命令是什么？ |
| 高风险点 | 哪些网络、权限、持久化、迁移或默认路径切换必须独立审计？ |
| 发布边界 | push、PR、CI、部署由谁触发？默认建议只由用户显式触发。 |

根 `AGENT.md`/`AGENTS.md` 只保留稳定项目事实、硬约束、当前入口和权威索引。代码地图、计划正文、历史、
流程问题和执行卡放到链接文档，避免根提示词不断膨胀和过期。

## 3. 风险模式

物化执行卡时选择最低足够模式。只有新证据改变了可达性、可逆性、权限或持久化风险时才升级。

| 模式 | 典型工作 | 默认保证 |
|---|---|---|
| `LIGHT` | 文档、小修复、内部重构、不可达 helper | 主代理自检和定向检查；不做外部审计 |
| `STANDARD` | 多文件实现、新内部合同、package data、可回退集成 | fast/direct、主代理收敛、按变更面门禁 |
| `STRICT` | 可达网络/凭据/进程/模型路径、持久化迁移、默认路径或高权限切换 | STANDARD 加稳定候选上的一次独立负向审计 |

问题按实际影响处理：

- 阻断数据损坏、权限逃逸、不可逆写入、核心合同失真和默认路径严重回归；
- 可达且较可能的问题，在修复成本与影响相称时修复；
- 理论加固、不可达场景、低影响改进和后续卡行为，明确记录后延期。

## 4. 角色与模型路由

主代理负责事实核对、合同冻结、任务交付、范围收敛、最终判断和提交。子代理只执行有界子任务；独立审计
者只读稳定候选，不参与施工。子代理默认不得继续创建子代理。

模型按复杂度选择，而不是固定使用某个模型：

| 工作 | 默认路由 |
|---|---|
| Git、文件集、退出码、测试执行、byte identity | 确定性工具，不用模型 |
| 机械且有界的编辑或结果分类 | 低成本模型，中等 reasoning |
| 常规实现和范围明确的诊断 | 均衡模型，中等 reasoning |
| 同一边界内的深推理或多模块合同 | 均衡/强模型，高 reasoning |
| 架构权威冲突或多个实质不同的有效设计 | 强模型高 reasoning；主代理先说明升级原因 |

如果平台提供 Luna/Terra/Sol，可分别映射为低成本、均衡和强模型；否则按平台等价能力替换。

动态升级规则：

1. 推理链变深但任务类型未变，先提高 reasoning；任务类型改变或当前模型不再产生新证据，再换模型。
2. 执行者必须交回新证据、已尝试路径和升级理由，由主代理决定升级、换模型或接管。
3. 同一根因两次修复仍不收敛，停止“验收—返工”，由主代理接管诊断；不得自动开启全面审计。
4. 工具、权限、依赖和环境故障不靠更强模型解决；难点结束后把机械工作降回工具或低成本路由。

## 5. 一张卡的执行循环

1. 主代理核对本地基线、用户改动、当前卡、读取集合、写集合及明确非目标。
2. 开工时公开模式、初始模型/reasoning、变更面、验证预算和停止条件。
3. 先完成第一条最小生产纵切，运行 `fast`；未取得反馈前不铺开完整实现或测试矩阵。
4. 多 family/多模块委派首次只授权第一条纵切。子代理交回 fast 证据后，主代理才释放卡内剩余范围。
5. 开发中只循环 `fast`；主代理收敛生产 diff、重复测试、范围和事实文档后运行 `direct`。
6. 按变更面运行额外门禁。失败后修复一次并只重跑直接受影响项。
7. 仅 `STRICT` 卡对稳定 staged patch 执行第 8 节的一次独立审计。
8. 证据收敛后更新事实层和计划状态，创建本轮唯一提交，并核对提交后的干净工作树。

这里的“第一纵切交回”是施工边界确认，不是一次外部验收，不运行全套 direct/package，也不产生提交。

## 6. 范围、搜索与停止条件

每张卡闭合一个主要生产权威，并至多迁移一个独立消费域。不要为了制造检查点而碎片化拆卡，也不要为了
避免重规划而偷偷扩卡。

执行者得到：

- 点名的事实/合同来源和起始符号；
- 精确或狭窄的允许读取范围；
- 精确写入路径；
- 正式调用者、非目标和保护集合。

搜索从点名符号和窄目录开始。扩大搜索范围前，执行者需说明缺失的具体事实及预期搜索边界。主代理在
direct/package 阶段观察是否出现全仓扫描、重复读取、无目的历史搜索或把确定性工作交给模型；这些通常是
交回变慢的信号，但应根据实际命令和产出判断，不能仅凭耗时推定。

结果只有三种：

- `ready`：约定边界和所选证据完成；
- `needs_replan`：权威、范围、依赖、权限、公共合同或持久化含义必须改变；
- `blocked`：计划仍有效，但外部条件阻止继续。

需要新依赖/凭据/权限、第二个主要权威、不可逆历史改写、隐式 fallback、无法证明的数据含义/来源/时间因果，
或两种合理解释会改变公共合同，应返回 `needs_replan`，不能靠提高模型能力自行决定。

## 7. 按变更面验证

项目应把命令填入执行卡，不要求所有卡都运行同一套门禁：

| 变更面 | 最小证据 |
|---|---|
| 纯文档 | diff 格式检查、链接、过期状态检索 |
| 实现/测试 | affected format/lint/type，加命名 fast/direct 测试 |
| package data/分发内容 | 实现证据，加 build 和隔离 package-loading/consumer check |
| 依赖、lock、toolchain | locked sync/install，加全部正式消费者门禁 |
| 新增可达能力 | 能力本身及一个正式消费者路径 |
| 里程碑、默认切换、发布 | 项目定义的完整本地门禁 |

约束：

- 同一生产拒绝点保留一个代表性回归；同一分支的值域优先参数化；
- coverage 是里程碑下限，不是测试数量目标；
- 不在测试器内递归启动 build、install 或另一套测试器；
- 不通过放宽 ignore、覆盖率或失败级别获得通过；
- 原样集成后的同一棵树不重复跑全量门禁；
- 远端 CI 不是本地开发的固定要求，只在项目发布流程或用户要求时使用。

## 8. 有界独立负向审计

外部审计只用于执行卡事先声明的 `STRICT` 能力激活点。审计前冻结既有不变量、正式可达面、非目标和
stable staged diff。审计者只读，不能添加新合同、假想消费者或相邻卡范围。

阻断 finding 必须同时给出：

1. 既有不变量；
2. 正式可达调用路径；
3. 普通输入或真实环境的最小复现；
4. 实际影响；
5. 当前卡内可完成的修复。

每个检查点最多经历：

1. 一次完整审计，一次性返回全部实质 findings；
2. 主代理一次集中修复，并只复跑直接受影响门禁；
3. 最多一次只核销原 findings 的 closure。

closure 只能因原 finding 未解决或修复直接引入严重回归而阻断。仍不通过时，主代理判断实现困难、审计
扩界或需要重规划，不能自动开始第二轮全面审计。生产合同没有变化时，不因测试或文档小修重开审计。

## 9. Git 与交接

- 审计和门禁收敛前保持工作树可见，不反复产生 `fix` 提交；
- 最终核对 staged diff 的文件集、diff check 和状态，再创建一个语义清晰的提交；
- 提交后核对 SHA、摘要和干净工作树；
- 不擅自 reset、覆盖用户改动、push、开 PR、合并或发布；
- 交接只保留：base/head、模式和升级、已实现/未实现、变更面和门禁、审计结论、已接受限制、回滚与下一卡。

详细命令日志只在失败且有诊断价值时保留。

## 10. 问题模式与流程演进

以下情况才增加一条最小 `process signal`：执行扩界、错误合同、重复验收/全量验证、模型路由失配、提交
污染，或明显增加时间/token 却没有新增相称证据。普通语法错误、一次性测试失败和及时闭环的普通修错不记。

记录格式：

```text
Process signal: <已有 ID 或 NEW> / <分类> / <直接证据> / <影响>
```

主代理在卡结束时去重：同一根因更新已有条目；一次重大或至少两张卡复发才修改全局流程。控制落地后先
标记 `MITIGATED`，经过两个相关检查点未复发再 `CLOSED`。不要为每次事件增加新字段、新门禁或新审计点；
如果固定流程成本高于问题的预期损失，继续观察即可。

## 附录 B：最小问题登记模板

只在达到第 10 节门槛后建立或更新：

```markdown
| ID | 分类 | 问题模式 | 出现情况 | 影响 | 当前控制 | 状态 |
|---|---|---|---|---|---|---|
| PI-001 | SCOPE | <共同根因，不写单次症状> | <卡/阶段> | <成本或风险> | <最小有效控制> | OBSERVING |
```

状态只用 `OBSERVING`、`ACTION_REQUIRED`、`MITIGATED`、`CLOSED`。分类建议固定为 `PLAN`、`SCOPE`、
`IMPLEMENTATION`、`TEST`、`VALIDATION`、`AUDIT`、`MODEL_ROUTE`、`GIT`、`ENVIRONMENT`、`HANDOFF`。

## 附录 C：迁移到新项目

1. 复制本文件，填写第 2 节的七项项目配置。
2. 在根 `AGENT.md`/`AGENTS.md` 中加入本文件链接和三条硬规则：最低足够风险模式、升级不扩权、稳定后一次提交。
3. 用附录 A 只物化**当前下一张**执行卡，不预生成全部未来卡。
4. 把目标项目的真实 format/lint/type/test/build 命令写进卡，不照搬来源项目命令。
5. 只列少数真正需要独立审计的能力激活点；其余使用主代理自检。
6. 前两张卡结束后复盘时间、token、返工轮数和逃逸风险，再删减或增强控制；不要在采用前把流程设计到最复杂。

建议观察四个健康指标：首次 fast 的时间、同根因返工轮数、无新增证据的验证/审计次数、执行卡外的读写
扩张。它们用于发现异常，不应自动变成新的强制门禁。
