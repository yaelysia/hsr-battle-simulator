# Agent Workflow and Validation Protocol

本文档定义 v8 的执行、验收和验证成本协议。它按需读取，不进入每个线程的自动上下文。

## 1. 目标

验证必须同时满足：

- 能发现真实代码和语义错误。
- 能证明来源、执行、settlement、replay 和 fail-closed 边界。
- 成本随本次改动范围增长，而不是随历史阶段数量增长。
- 历史 evidence 可追溯，但不会成为永久重跑负担。

严格性来自准确谓词和真实调用链，不来自脚本数量。

## 2. 单一事实位置

- 当前状态：`CODEX_HANDOFF.md`
- 长期架构：`ARCHITECTURE_BOUNDARY_CONTRACT.md`
- 禁止行为：`FORBIDDEN.md`
- 阶段目标：对应 task plan 的唯一 checklist
- 单阶段实施：对应 execution card
- 执行 evidence：`ready_for_review` 报告
- 验收结论：checklist、checkpoint 和 Git 提交

禁止在 `AGENTS.md`、文档索引和多个报告中重复维护当前阶段状态。

## 3. 线程职责

### 规划线程

- 根据当前代码、来源和依赖设计阶段目标。
- 一张卡只覆盖一个阶段。
- 目标写清完成后系统具备的能力、明确不做的相邻范围。
- 验收写清允许通过、必须失败和对应证据。
- 先区分真实 source gap、lowering gap、admission gap、implementation missing 和 validation gap。
- 不要求执行线程为当前来源不存在的机制伪造 executable 正例。
- 写卡前先完成一页以内的闭合地图：权威分母、输入/输出权威、生产不变量、全部正式调用者、
  精确 gap owner 和最小证据。这张地图是阶段范围契约，不是实现步骤教程。
- 若来源是具有可扩展 schema 的对象，闭合地图必须列出记录分母和字段分母。未知同级字段只能
  被明确分类、裁决排除或阻断整条记录；不得在只读取几个已知字段后宣称目录完整。
- family 分母必须来自来源投影中的类型化语义和 scope；名称前后缀或当前实现列表只能辅助诊断。
  非战斗排除必须继续解析受控分支中的 ability/template 跳转并检查实际末端，无法闭合就保守阻断。
- 若目标同时新建数据权威、改变外部交互契约并迁移执行期上下文，且三者可分别验收，
  必须按权威边界拆分；不得用扩大执行卡来换取少一个阶段名。
- 若真实机制已闭合，但完整内容动作仍被后续阶段的独立能力图缺口阻断，必须把“机制验收”
  和“内容端到端回验”拆成两个明确状态。前者可留 accepted evidence，阶段总项保持未完成，
  并写出唯一返回条件；不得删减真实任务或伪造动作来凑端到端正例。

### 执行线程

- 只读核对当前卡和直接代码事实。
- 事实偏差改变目标或验收时停止并交回规划线程。
- 只实施当前卡，不提前进入下一阶段。
- 修改后检查生产代码，不以验证脚本变绿代替自审。
- 最终状态只能是 `ready_for_review`。
- 不勾 checklist、不提交 Git、不复述整张执行卡。

### 验收线程

- 先看 diff、生产调用链和数据边界，再选择验证。
- 检查通用性、扩展性、来源真实性、失败原子性和验证谓词质量。
- 一次性汇总当前可发现的阻断，避免逐轮挤出问题。
- 报告只作为 evidence 索引，不能代替代码复核。
- 通过后更新 checklist，并提交范围干净的检查点。

首次验收在对外提出任何整改意见前，必须完成五面审查：

1. 从权威来源重建记录分母与结构化对象的字段分母，再重建阶段完成集。
2. 检查生产构造、lowering、提交及 runtime 边界的不变量和原子失败。
3. 用调用图核对所有正式生产调用者与旧语义残留。
4. 核对每个 gameplay gap 的原因、代表来源和唯一后续 owner。
5. 审查验证器的独立分母、fixture 合法性、总门类型语义和资源真实性。

验收线程应先在内部形成完整 finding ledger，然后一次性提交。修复复核可只审差量，
但仍要重跑低成本的来源范围门和 gap 归属门。一次集中修复后仍出现新的系统性问题类别，
说明闭合地图或阶段分解有误；此时先重新规划，不继续堆叠局部修复轮。

阶段唯一主入口不是开发调试循环。生产实现完成后先做调用图、来源末端和负例静态审查，
五面 finding ledger 闭合后才运行主入口；此前只允许 `compileall` 和单个生产不变量的最小探针。

## 4. 执行卡最低内容

每张执行卡只保留一套完成清单，并包含：

- 一页以内的闭合地图，其中完成集使用当前来源或正式调用者分母，不使用固定数量。
- 阶段背景和前置检查点。
- 详细阶段目标。
- 本阶段只做。
- 本阶段不做。
- 架构归属和禁止做法。
- 目标与证据映射。
- 结构化通过谓词。
- negative matrix。
- gap、blocked、deferred 和 not-proven 口径。
- 拟改生产文件和验证文件。
- `fast`、`direct`、条件触发验证。
- 明确不跑的验证及原因。
- IO、内存和输出体积限制。
- `[ ]` 完成项。

对话发起只需要执行卡路径、基线提交和范围约束，不粘贴卡片全文。

## 5. 缺口分类

任何机制先判断：

1. raw TBGD 是否有结构化来源。
2. lowering 是否完整投影。
3. RuleBook 是否保留执行所需类型字段和审计来源。
4. runtime 是否通过通用系统消费。
5. validation 是否使用准确的结构化谓词选样。

分类：

- `executable`：真实来源、mutation、settlement、source audit 和 replay 闭合。
- `source_gap_blocked`：raw 来源确实不存在，验证 blocked/state unchanged。
- `lowering_gap`：raw 有来源但 IR 未完整投影。
- `admission_gap`：IR 有来源但未准入执行。
- `implementation_missing`：已准入来源缺少正确 runtime consumer。
- `validation_gap`：生产路径可能完整，但当前验证没有正确证明。
- `deferred`：用户明确调整优先级，尚未执行。
- `not_proven`：没有证据，不能解释成通过或失败。

`ok=true` 不得覆盖内部 gap；聚合必须继承分阶段缺口。

### 产品范围待裁决

`scope_decision_required` 表示来源真实，但是否属于战斗模拟器成品范围尚未由用户裁决。
它不是 source gap，也不能由执行代理自行解释为必须兼容。

执行代理应在不污染架构的前提下继续互不依赖的工作，并提交一条简洁记录：

1. 该内容在实际游戏中是什么。
2. 当前代码为何在这里阻断。
3. 它是否改变战斗输入、动作、状态转移或结算。
4. 纳入实现的成本、通用性影响和不实现的后果。
5. 推荐现在实现、以后实现、仅目录保留或明确排除。

若该裁决不影响本阶段其余目标，可以不中断施工；但它影响阶段完成范围时，必须在
`ready_for_review` 前向用户说明，不能自行勾选。若继续施工必须先选择不可逆架构方向，
则立即暂停。

## 6. 四层验证

### Fast

每次修改默认运行：

- 触达 Python 包的 `compileall`。
- 当前阶段聚焦验证或最小测试。
- `git diff --check`。

目标是快速发现语法、局部契约和格式错误。

### 聚焦验证结构

- 一个阶段只有一个权威业务入口和一份 summary。额外入口只能用于一次性定位问题，
  不得与主入口重复证明完成谓词，也不得成为提交门。
- 每个业务不变量只在最靠近其生产边界的一处验证。模型 codec、递归不可变、
  fingerprint、场景准入等既有契约在未触达时直接继承，不复制到新阶段矩阵。
- 聚焦验证只构造本阶段需要的最小真实对象。不得为局部目录或装配规则手工重建完整
  角色、敌人、动作、场景和 Canonical IR；若只能这样验证，应先补生产窄入口或缩小
  阶段目标。
- 执行卡必须同时限制业务入口数、来源读取次数、fixture 数、验证代码规模、墙钟、
  峰值内存和 evidence 体积。任一项预计超限时先暂停修订计划，不能通过增加 CLI mode、
  拆分文件或重复 direct 绕开预算。
- 阶段通过后立即判定验证器生命周期。默认冻结为 `historical_evidence`；只有稳定、
  轻量且被后续真实调用链直接依赖的切片才保留为 `active_contract`。
- 目录或来源完整性的分母必须由 raw inventory、已确立的生产投影或全部正式调用者独立导出；
  不得使用当前实现已返回的 kind/ID 反向定义通过集。
- 对结构化配置，验证器应独立枚举实际同级字段并与生产分类逐项对账；代表样例只证明语义，
  不能替代字段分母。生产模型应自行拒绝“字段来源与规范化结果不一致”，验证器只保留一个聚合门。
- 当真实内容因后续阶段缺口尚不能走完整执行链时，必须把证据拆成“真实来源语义”和“通用执行
  上下文运输”两栏：前者使用真实目录或窄投影，后者可以使用明确标注的最小 validation fixture。
  两栏互补但不能互相冒充；fixture 通过不得被汇报为真实 gameplay 已 executable，真实来源存在也
  不能替代调度、提交和 replay 连续性的生产边界证明。
- 对会先写队列、阶段或 committed state、再由下游执行器消费的请求，验收必须检查首次 mutation
  之前的 actor、所有权、submission admission 和上下文门；“最终执行会失败”不能替代入口原子性。
- 对 UI/adapter/solver 入口，命令身份必须从被选中的内核 choice/template 原样派生。验收至少检查
  一条“选择 actor 与当前画面/行动条 actor 不同”的路径，防止展示状态成为第二套命令规则。
- 总门必须对 `bool`、`int`、空集合和 blocked 状态做精确类型判断，并至少用一个本应失败的控制探针
  证明总门不会假阳性。
- 任何 `all()`、子集或“全部已闭合”谓词都必须同时说明空集语义：要求存在真实记录时显式检查
  非空；允许真实空集时由独立来源分母证明为空。不得让 `all([])` 充当机制完成证据。
- 验证代码行数是防膨胀护栏，不是必须压到的目标。若证据在可读实现下超预算，应缩小阶段或
  把错误移入生产不变量，不得用高密度压行绕过上限。

### Direct

只运行与本次生产修改存在调用链或数据契约关系的现行回归：

- reducer 改动：原子提交、before 冲突、replay。
- target 改动：query-submit、目标基数、空集合和失败三态。
- status 改动：生命周期、概率、callback、source audit。
- scheduler/timeline 改动：阶段、队列、行动值和前进保证。
- summon/wave 改动：出生、关系、清理、波次生命周期。
- RNG 改动：事件身份、选择账本和 replay。

执行卡必须说明为什么该回归与当前调用链直接相关。

### Catalog

用于证明完整来源或内容目录：

- 来源清单和指纹变化。
- lowering 或定义目录变化。
- RuleBook 目录索引和冲突处理变化。
- 正式目录 admission 或 startup 变化。

要求：

- 一次读取来源后复用。
- 按批次处理，峰值不随目录线性增长。
- 不默认写完整 Canonical IR 或 RuleBook。
- 输出集合摘要、缺口矩阵和少量样本。
- 未执行时标记 `not_proven`，不能由 fixture 替代。

### Full

只在以下情况运行：

- 里程碑最终聚合。
- 共享内核大规模重构。
- source/lowering 全局语义变化。
- 用户明确要求。

Full 不是小阶段默认提交门。

## 7. 历史验证生命周期

现有阶段脚本必须逐步归类：

- `active_contract`：仍表达当前生产契约，可作为 direct 回归。
- `catalog_audit`：重型来源或目录证明，只按触发条件运行。
- `historical_evidence`：只证明旧检查点，不再默认执行。
- `superseded`：谓词已被新验证完整替代，保留归档说明后退役。
- `invalid`：依赖过时或错误语义，不能通过修改生产代码迁就。

迁移规则：

- 保留仍有效的谓词，不保留旧脚本结构本身。
- 已验收阶段脚本不得因后续阶段需要而持续扩写。后续确实改变共享生产契约时，只提取
  受影响谓词形成小型 direct；旧脚本仍保持冻结。
- 复用先发生在一个真实重调用链内部：同一进程共享构建结果和公共证据，再由小型
  断言消费。不要先建立全项目注册表或调度框架。
- 提取公共路径时必须在同一改动中删除被替代的重复实现；只移动代码、增加包装层
  或保留新旧双轨不算迁移。
- 至少两个独立真实消费者证明输入、生命周期和失败语义相同后，才允许提取跨阶段
  公共组件。
- 不为大型验证工具另写同等规模的“验证验证器”。直接对真实输出、构建次数和
  现行谓词做验收。
- 同一轮完整 lowering 最多一次。
- 旧脚本失败时先判断契约是否仍有效，再决定修测试还是修生产。

## 8. 资源约束

- 所有重验证串行执行，使用低 IO/CPU 优先级。
- 输出写入 `/tmp`。
- 默认只写 summary、matrix、负例和抽样审计。
- 大产物必须有显式开关，默认关闭。
- 不并行构建多个完整 RuleBook。
- 重验证优化必须记录实际构建次数、墙钟时间和峰值内存；纯验证治理的 Python
  代码量原则上必须净减少。
- 同一聚焦入口需要多个大型目录时，按证据阶段顺序构建并及时释放已消费对象；不得为了调用
  方便让完整卡目录、来源目录和动作切片同时常驻。压缩输出不能替代对象生命周期收缩。
- 来源缓存只能是验证优化，生产代码不能依赖 `/tmp` 或验收产物。
- 缓存键至少包含来源指纹、lowering 版本和影响语义的配置。
- 缓存损坏、键不匹配或来源变化必须 fail-closed 并重建。

## 9. Token 协议

- 常驻 `AGENTS.md` 只保留稳定红线。
- 当前状态只在 `CODEX_HANDOFF.md` 维护。
- 执行卡只写文件一次，对话不重复全文。
- 新线程只读当前卡和直接依赖。
- 执行汇报限制为：状态、变更范围、验证结果、遗留 gap、报告路径。
- 验收汇报限制为：结论、阻断、已验证范围、未验证范围。
- 命令原始日志不粘贴到对话；保存到 `/tmp`，只读取 summary。
- 修复轮只发送差量阻断，不重新讲完整项目背景。
- 历史经验按关键词从 archive 和 checkpoint 检索。
- 每阶段报告记录实施轮数、验收轮数、首次 findings 类别、修复后新增系统性类别和主验证运行数，
  用阶段总成本而非模型名称评估工作流。

## 10. 并行和模型分工

- 同一工作区不并行写代码。
- 独立阶段只有写集合互斥、依赖图明确且基于同一检查点时才能使用独立 worktree。
- 新共享机制、架构和验收使用强推理模型。
- 现有契约下的数据卡扩面、机械投影和固定矩阵可使用成本更低的模型。
- 低成本模型不能自行修改目标、放宽验收或解释未知机制。

## 11. 提交边界

阶段检查点只包含：

- 本阶段生产代码。
- 本阶段验证。
- 对应 execution card、报告和 checklist 更新。

不混入：

- 无关 UI 草稿。
- 相邻阶段预实现。
- 临时产物。
- 仅为旧接口兼容的污染。

纯规划和说明文档默认随最近一次相关检查点提交，除非用户明确要求独立提交。

## 12. 当前验证治理待办

`VG-S1` 和 `VG-S2` 已分别关闭 committed state 可变绕过和生命周期提交完整性
绕过。原 `VG-S3` 全项目 validator registry 路线已撤销：它先增加了新的治理
系统，却没有在同一阶段减少真实重构建、历史脚本或运行成本。

当前唯一试点是 P8-S8 的 task/event 两条契约路径。两条路径读取相同来源、构建
相同 owned-combatant 目录，并重复生成同一组公共事件证据。第一次基线还证明
单条路径为五类 servant 准入数据调用完整 lowering 会在 4 GiB 内存上限下失败。
试点只做：

1. 在 lowering 层用现有生产语义建立 owned-combatant 准入窄投影，删除
   P8-S8 对完整 `TBGDLowering.build()` 的依赖。
2. 在一个进程内构建一次共享上下文。
3. 从该上下文分别计算 task 和 event 现行谓词。
4. 保留旧单切片命令作为同一实现的薄路由，并提供一次运行两个切片的入口。
5. 删除被替代的 full-build 与重复编排，记录构建次数、耗时、峰值内存和代码量。

试点未证明收益前，不建立跨项目注册表、持久缓存、通用调度器或后续治理阶段族。
试点通过后只选择第二个真实重复点复核边界；只有两个独立消费者形态一致时，才
讨论公共抽象。事件所有权和其他状态权威问题仍按生产机制单独制卡，不能借验证
治理扩大范围。
