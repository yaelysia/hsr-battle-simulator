## 1. 优化目标

工作流优化的是预期工程损失，而不是验证数量：

```text
总成本 = 实施成本 + 验证成本 + 返工成本 + 缺陷进入后续阶段的风险成本
```

原则：

1. 非法状态优先在生产构造、准入或提交边界暴露。
2. 验证只观察本次改动新增或改变的行为，不重新证明整个项目。
3. 一张卡只建立一个主要权威，形成最小但完整的生产纵切。
4. 同类问题集中修复和集中验收；不围绕主验证逐例打补丁。
5. 更强模型提高判断质量，不扩大任务范围、写集合或验证预算。

## 2. 风险模式

规划线程根据实际改动面选择最低充分模式。文件少不代表低风险；触达共享权威时必须升级。

### LIGHT

适用：

- 文档、报告、注释和索引；
- 局部开发工具；
- 可机械确认不改变行为的内部整理。

要求：目标、允许写集合、非目标、fast 命令。通常不新建专项报告和长期验证器。

### STANDARD

适用：

- 新增一个内部类型契约；
- 修改一条 lowering 路径或一个独立消费域；
- 可逆的局部功能和边界迁移；
- 不涉及正式状态提交、全目录完整性或共享执行语义。

要求：一页以内执行卡、最小生产纵切、每个新增不变量一个最小反例、fast 和必要 direct。

### STRICT

任一条件成立即使用：

- 声称完整覆盖真实来源、角色、怪物、装备、模板或目录；
- 修改共享 lowering、RuleBook 全局索引或公共执行入口；
- 修改 committed state、原子提交、mutation、event、RNG、settlement、snapshot 或 replay；
- 迁移公共契约、删除回退、影响多个独立正式消费者；
- 一次失败可能静默产生错误战斗结果或错误来源审计。

要求：在 STANDARD 基础上增加与改动面对应的独立来源分母、原子失败或连续性证据；只有需要时
运行 catalog。独立反例审计只属于 STRICT，不能附着到普通卡上。

### 升级规则

实施中发现以下事实时停止并升级或重拆：

- 出现第二个未声明的生产权威；
- 必须迁移第二个独立消费域；
- 需要修改两个以上未列出的生产文件；
- 实际触达比卡面更高的风险边界；
- 首次集中审查出现三个以上系统性问题类别。

不能通过写更长的执行卡把两张 STRICT 卡压成一张。

## 3. 单一事实位置

- 核心项目检查点：`CODEX_HANDOFF.md`；MCP 任务状态、claims 和 Finding Ledger：`.local-workflow/` 任务账本。
- 总目标和阶段顺序：当前阶段总计划及唯一 checklist。
- 单阶段范围：当前执行卡。
- 架构：`ARCHITECTURE_BOUNDARY_CONTRACT.md`、`FORBIDDEN.md`。
- 工作方式：本协议。
- 实际证据：当前源码、必要的验证报告；MCP Reviewer 只能引用已推送 PR、commit 和 GitHub 可见的 CI/评论。

执行卡不得复制大段历史背景或任务账本；只写影响本卡实现的事实、决定及其权威引用。

### Gap 口径

只在阶段涉及真实内容覆盖或存在未闭合项时使用以下分类：

- `source_gap_blocked`：raw 结构化来源确实不存在。
- `lowering_gap`：raw 有来源，但 IR 未完整投影。
- `admission_gap`：IR 已保留来源，但正式执行尚未准入。
- `implementation_missing`：已准入来源缺少正确 runtime consumer。
- `validation_gap`：生产路径可能完整，但当前 evidence 尚未证明。
- `deferred`：已明确调整优先级，当前不实施。
- `not_proven`：没有足够事实，不能解释为通过或失败。
- `scope_decision_required`：来源真实，但是否属于战斗模拟范围需要用户裁决。

`ok=true` 不能覆盖 gap。`scope_decision_required` 必须说明内容是什么、是否改变战斗、实现代价和建议；
继续实施若需要不可逆架构选择，则在用户裁决前暂停。

## 4. 规划前事实核对

规划线程先形成短导航摘要，不让执行线程重新探索项目：

1. 精确起始符号和现有调用链。
2. 本卡唯一生产权威、输入和输出。
3. 受影响的正式调用者。
4. 已确认的来源或业务语义。
5. 真正待解决的问题和明确 deferred。
6. 允许写集合、最早可编译纵切和停止条件。

仅在以下改动中补充“闭合地图”：

- 来源或目录完整性：权威分母、引用作用域、缺省语义、排除依据。
- 树、图或状态机：真实 child、分支、循环和命名作用域。
- runtime/提交：producer、admission、mutation、候选状态、settlement/replay 连续链。
- 公共迁移：全部正式调用者、旧域归属和回退删除条件。

普通 STANDARD 卡不需要扫描完整值域、全目录或无关消费者来证明“没有遗漏”。

## 5. 执行卡最小内容

每张卡使用附录的七块固定核心，长度随风险变化；不为不适用的栏目编造生产权威、消费者或来源分母。
卡面可引用任务账本中的 claim ID 和 reuse obligation，不复制其完整内容；任务状态仍以账本为准。
Success Criteria 描述可观察的生产结果，不以某个测试通过代替目标；验证命令单列为证据。
卡片不设 Reviewer Checklist：REVIEW 依据目标、成功条件、项目不变量和实际交付独立审计。

### 所有模式

- 风险、目标、可观察成功条件；
- 影响本卡的已确认 FACT（附证据）、已批准 DECISION，以及尚待验证的 HYPOTHESIS；
- 涉及生产代码时的权威、正式消费者和应复用的现有机制；
- 允许写集合、非目标和 deferred；
- 必跑 fast、必要 direct，及确有成本风险时的资源预算；
- `needs_replan` / `blocked` 停止条件和交付证据位置。

### STANDARD 追加

- 最小完整纵切；
- 新增生产不变量及其最小反例；
- 受影响调用者的迁移完成条件。

### STRICT 追加

- 独立分母或原子链的权威来源；
- fail-closed 和 state unchanged 条件；
- catalog/full 是否触发以及原因；
- 未闭合真实内容的精确归属和唯一回验条件。

不要为验证器行数、生产新增行数设置常规硬指标。只有已有明显膨胀风险时才设预算；预算用于暂停
和重拆，不用于压缩排版。

来源、Runtime/Mutation、RNG/Event、公共迁移和接管既有 PR 的专用契约只在实际触及时追加。
来源卡要求正式 IR 可追溯到权威来源；只有声称目录/集合闭合时才要求分母、分区和双向集合差，
不笼统要求字面上的 source → IR 可逆。

## 6. 执行循环

```text
刷新相关事实 -> 最小纵切 -> 必跑验证 -> 轻量 DELIVERY_CHECK -> 按任务工作流交付 -> REVIEW
```

执行要求：

1. 最多两轮结构定位；出现具体未解析依赖时再扩大阅读。
2. 尽早形成可编译纵切，不先写大型验证器。
3. 只有目录或多来源 family 卡才分两段授权：先让一种真实来源形状穿过既定权威，fast 通过后再展开
   同类分母；不得按固定角色或 ID 选择一个“代表样例”冒充来源形状。
4. 开发中间态使用编译和单个最小反例；主入口不是调试循环。
5. 先让生产边界拒绝矛盾状态，再为该不变量保留一个反例。
6. 执行卡列明且仍然有效的验证是必跑下限。新发现的直接回归可补最小定向检查，
   不自行扩大到无关 catalog/full；指定命令不能运行时报告阻断，不静默以别的命令冒充通过。
7. EXEC 只做已有 `DELIVERY_CHECK` 的范围、必跑验证和计划一致性三项，不重新做完整审计。
   已确认 FACT 的依赖变化先按任务账本刷新；仅当变化影响已批准决定、范围或成功条件时 `needs_replan`。
8. 不自行修改 checklist 或进入下一阶段。MCP 工作流任务按批准计划提交、push、新建或更新绑定的 PR，
   但不 merge；非 MCP 任务仅在任务明确授权时自行提交 Git。

执行状态只有：

- `ready_for_review`：卡面目标和轻量交付检查均完成；MCP 工作流由协调器转入 `awaiting_audit`。
- `needs_replan`：批准的决定、风险、写集合或成功条件与现实发生实质冲突。
- `blocked`：外部来源、环境或产品裁决阻止继续。

同一根因修复两次仍失败时停止补丁循环；MCP 任务交协调器路由，非 MCP 任务交规划/验收线程接管或重拆。

## 7. 生产自审与验收

本节的集中审查属于 REVIEW/验收者，不是 EXEC 的第二份交付检查。MCP 工作流的 Reviewer
只通过 GitHub 审计已推送的精确 PR HEAD；本地未提交事实不得冒充 GitHub 可见证据。

### 通用审查

以下是审计视角，不是额外的完成定义。阻塞性 finding 必须指向成功条件、批准计划、确定性失败、
具体回归或项目既有不变量；偏好的“更优雅实现”不能阻塞。每次都检查：

- 生产代码是否真正实现目标，而非只让验证变绿；
- 是否出现固定 ID、名称、文件、hash、观测答案或第二套解释器；
- 允许写集合和架构边界是否守住；
- 验证总门是否会因空集、布尔数值混淆或错误退出码产生假阳性；
- deferred 是否准确，没有把 blocked/fixture 伪装成 executable。

### 按改动面启用的审查

| 改动面 | 必须追加检查 |
|---|---|
| 来源、lowering、目录 | 适用时的独立分母与双向集合差、正式 IR 到权威来源的追溯、引用作用域 |
| runtime、状态提交 | 首条 mutation 前准入、失败零副作用、settlement/replay 连续性 |
| 公共契约迁移 | 正式调用者已迁移、正式域无双写/回退、旧内容域有归属 |
| 构筑或 scenario | 重复身份一致、装配与 runtime 权威隔离、非法输入 fail-closed |
| RNG 或事件 | producer 身份、消费顺序、RNG/event/replay 身份一致 |
| 完整性声明 | 每个 gameplay gap 有精确后续阶段或已裁决排除依据 |

未触达的审查面不重复展开。旧版固定“五面审查”被该选择表替代。

### 验收节奏

首次 FULL_AUDIT 应完成所有适用审查后一次性给出 findings，不得检出一项就提前结束。
返修后的 CLOSURE_AUDIT 只核销原 finding、检查返修直接引入的回归及必要的低成本范围门；
不从零重审整个任务。若出现新的系统性问题类别，先判断是返修回归、首轮遗漏还是新近可见事实，
再决定修订规划，不继续堆补丁。

## 8. 验证分层

### Fast

默认必跑：

- 触达模块的 `compileall` 或类型检查；
- 本阶段唯一聚焦入口，或没有必要时的最小反例；
- `git diff --check`。

新增可执行验证模块时先做一次 import-only smoke；`compileall` 不能证明导入符号存在。

LIGHT 可以只有编译、静态检查和 diff。不得为了形式完整而新建验证器。

### Direct

只运行本次调用链直接触达的现行契约。运行前确认脚本仍是 `active_contract`；历史 evidence、已替代
语义和无调用链关系的脚本不得顺便运行。缺少现行 direct 时使用一个临时最小探针，不升级成新框架。

### Catalog

仅在来源发现、lowering、引用闭包或目录准入变化时运行。过滤必须在来源投影和 IR 构建前生效；
先完整构建再过滤输出不算聚焦验证。

### Full

只在重大架构修改、阶段聚合、发布里程碑或用户明确要求时运行。普通阶段不得以 full 作为完成门。

### 资源规则

- 串行、低优先级，产物默认写 `/tmp`。
- 不默认输出完整 Canonical IR、RuleBook、transition、coverage 或 fidelity。
- 执行卡按预计成本给墙钟、峰值内存和产物预算；达到约 70% 时先复核范围。
- 验证超预算先缩小来源和入口，不增加 CLI mode、缓存层或“验证验证器”。
- 同一业务不变量只有一条权威验收路径；诊断探针不能成为并列完成门。
- 不手工搭建与阶段无关的完整角色、敌人、动作或 Canonical IR 世界；缺少窄生产入口时先缩卡。
- 验证器不得重组动作、伤害、召唤或提交顺序替代正式入口；只有 `tools/` 调用的新 API 不能作为
  gameplay 闭合证据。

## 9. HSR 严格证据配置

以下规则只在对应 STRICT 改动触发时启用，但一旦触发不得放宽。

### 来源与目录

- 完成分母由类型化语义分类生成，不能由名称正则、当前支持列表或固定样例定义。
- 记录集合和对象内同级字段都要有归属：战斗语义、明确排除或 fail-closed。
- 完整定义目录不等于可执行入口；执行分母从真实 producer 根节点沿类型化调用边得到。
- 上游 owner/container blocked 只能阻止执行，不能让真实 child/callback 从目录消失。
- 共享模板的 raw occurrence 身份与 owner 图位置身份必须分开。
- 排除表现分支要闭合到实际末端；存在未解析跳转时只能保留或阻断。
- task 子集、启动项和准入过滤只能在完整 entry/graph/owner/task 身份闭合后发生。
- 控制流分支按来源的类型化 kind/label 选择；单一 child 不代表无条件执行。
- 主入口前允许一次不落盘的独立集合差；未归零不得用主入口逐条调试。

### 状态与执行

- 公开请求在第一条 mutation 前验证 actor、动作所有权、admission 和重复身份字段一致。
- 正式分支缺图或执行失败时不得回退旧解释器。
- 公共 API 同时服务正式域和待迁移域时，在最外层按类型化 producer/invocation role 分流，不能按
  名称、ID 形状或目录命中猜测。
- 领域 hook 只返回 mutation、event、RNG、settlement 和类型化 outcome；共享执行器唯一归并候选状态。
- event evidence 必须保留同一链上的生产前状态、mutation、候选状态和派发结果。
- settlement 不能从日志事后反推；replay 必须验证正式状态连续性和身份一致。
- invocation 天生缺少领域上下文时，应在进入对应 admission 前按类型化角色阻断，不能伪造上下文穿过。
- UI、适配器和推演器提交的 actor/action/level 必须来自内核 choice/template，不能从行动条焦点或
  列表首项反推。

### Fixture 与真实内容

- `validation_fixture` 可以证明通用组件或调用形状，不能证明真实角色、怪物或装备 executable。
- blocked/deferred 只作为负例或 gap，不能进入正例分母。
- `all()`、子集和“全部通过”必须显式裁决空集语义；需要真实正例时同时证明非空。
- 外部内容尚无真实 producer 时保留 `not_proven`，不得合成 gameplay producer 冒充闭合。

## 10. Evidence 与文档

- LIGHT 默认不写 `ready_for_review` 报告，除非需要跨线程交付。
- STANDARD 报告只索引实际改动、命令结果、deferred 和资源异常，不复述执行卡。
- STRICT 报告增加独立分母、原子链或 catalog 结果。
- 阶段验证验收后默认标记为 `historical_evidence`；只有稳定、轻量、单职责的切片才保留为
  `active_contract`。
- 局部 bug 留在阶段报告；只有重复出现或会影响后续阶段的经验才更新本协议。

报告中的 `ok=true` 不是验收裁决。业务 CLI 退出码只服从业务结果，治理指标和允许 gap 不能把业务
失败改写为成功。临时已知 gap 是允许上限，必须允许减少到零，不能要求旧失败永久存在。

## 11. HSR 执行角色与可选模型路由

PLAN 负责事实核对、风险定级、执行卡及需用户批准的决定；EXEC 在写集合内实现、验证和交付，
不重新设计架构；REVIEW 独立审计；MCP 协调器维护任务状态并执行受控合并。
不使用 MCP 工作流时，主线程可兼任 PLAN、验收和检查点职责，但不能把同一上下文的复读称为独立审计。

这些是逻辑职责，不以平台具有子代理 API 为前提。实际执行方式按当前环境选择：

- 支持子代理：主线程可派生干净上下文执行一张有界卡，子代理默认不得继续派生下级代理。
- 不支持子代理：主线程顺序实施，或由用户把同一张卡交给新的人工线程。
- 只有外部 CLI/ACP：主线程把它视为受控执行工具，限制工作目录、写集合和权限，并复核实际 diff。
- 不能选择模型或推理强度：使用当前可用模型，风险模式和验收标准不变；必要时缩小卡片或由主线程
  承担高风险部分，不能假设不存在的升级能力。
- 不具备独立上下文：不得把同线程第二次阅读称为独立审计。

不得为了获得子代理能力自行安装依赖、连接外部服务或扩大权限。需要这些能力时按项目的新依赖和
权限规则先向用户申请。

独立执行者只接收 HSR 窄导航：起始符号、Canonical IR/数据卡/runtime 中的权威位置、正式调用链、
已确认来源形状、允许写集合和不得参考的历史路径。

### 模型可选时的初始路由

| HSR 任务形状 | 初始路由 |
|---|---|
| Git、文件集、运行命令、来源计数和集合差 | 确定性工具 |
| 文档、报告、机械迁移和已冻结 schema 下的批量数据卡 | Luna/Terra，中等推理 |
| 单一 IR/codec、一个 lowering 或一个独立消费者 | Terra Max |
| 跨模块身份与来源运输、多个正式调用者迁移 | Sol Medium/High |
| 共享执行器、状态提交、event/RNG/settlement/replay 或架构权威冲突 | Sol XHigh/Max 或主线程直接实施 |

这个路由是成本建议，不是执行前提。它来自本项目既有经验：较低成本模型可以稳定完成边界明确的生产
编辑，但在来源真实性、跨入口连续性和自我验收上容易遗漏。不能通过把卡写得更长，把最后两类任务
强行降给低成本模型；平台不能换模型时，应改由主线程处理高风险部分或进一步拆卡。

### 升级裁决

主线程先判断失败属于哪一类：

1. `context_gap`：缺少具体符号、调用链或来源形状。主线程补一段窄导航，原模型继续，不立即升级。
2. `needs_replan`：出现第二权威、第二消费域或卡面语义错误。重新拆卡，不能靠更强模型吸收范围。
3. `capability_gap`：事实和契约都已冻结，但执行者仍反复伪造来源、写专属分支、复制第二套规则，或
   无法在既定边界形成纵切。先提高推理强度；仍无新证据再换上一档模型。
4. `validation_cost_gap`：完整 lowering、历史 direct、产物或内存超预算。收缩投影和证据，不升级模型。
5. 环境、权限、依赖故障：修复环境或提交 `blocked`，不升级模型。

升级能力存在时，请求必须包含：新事实、已经尝试的路径、当前 diff 是否可保留、剩余问题和建议路由。
主线程决定继续、升级、换模型、接管或回退。能力不存在时直接在“接管、缩卡、重新规划”中选择。
相同根因两次修复仍不收敛时由主线程接管，不再派第三个执行者。
困难的共享语义闭合后，剩余机械迁移应重新降回 Terra 或工具，避免整卡持续使用高成本模型。

### 本项目的验收代理规则

以下限制只针对非 MCP 工作流中额外派生的辅助验收代理；不取消 MCP 工作流要求的 GitHub Reviewer：

- 非 MCP 执行代理只能提交 `ready_for_review`；最终验收和检查点由主线程负责。
- LIGHT/STANDARD 不额外派独立验收代理。主线程按第 7 节对实际改动面做一次集中审查。
- STRICT 也不默认全量二次审查。只有平台支持独立上下文，且主线程能指出一个具体高风险问题，例如
  “来源身份能否伪造”或“失败是否可能留下 mutation”，才可让独立执行者只读寻找该类反例。
- 辅助验收代理不得运行全量验证、扩展阶段范围或产生新的流程门；其 finding 必须由主线程结合生产
  代码复核。这个限制用于避免本项目曾出现的高误报、重复验收和额外 token 消耗。
- 一次集中修复后只核销原 finding；若出现新的系统性类别，返回规划阶段，不继续串联验收代理。

## 12. Git 与并行

- MCP 工作流中，EXEC 只提交批准范围内的改动并 push 到任务绑定分支；新任务建立 PR，接管任务
  只更新原 PR。Reviewer 不改本地文件，只有协调器在精确 HEAD 的 PASS 和本地合并门禁满足后 merge。
- 非 MCP 任务只有在明确授权时由执行线程提交 Git；验收通过后由项目权威维护 checklist 和检查点。
- 未获用户接受的语义阻断不能提交完成检查点。
- 无关修改保留且不混入；纯规划文档按获批任务的写集合处理，不自动混入下一实现提交。
- 并行只允许依赖清晰、写集合互斥并从同一检查点创建的独立 worktree。

## 附录：执行卡模板（固定核心 + 条件模块）

```markdown
# <CARD_ID> — <完成后的结果>
> Parent Plan: <路径或任务 ID> | Risk: LIGHT / STANDARD / STRICT
> Upstream: <必须已完成的前置卡；没有则 none>

## 1. Goal / Success Criteria
- 目标：完成后系统具备什么行为或事实，不列改动文件。
- 成功条件：2–7 项可观察结果；测试通过写在验证栏，不代替结果。

## 2. Confirmed Context / Decisions
- FACT：仅列影响本卡的已核实事实，附源码、blob、PR 或 claim ID；注明 local-only 事实。
- DECISION：已批准的范围、架构、兼容性决定；没有则 none。
- HYPOTHESIS：待验证假设，不冒充 FACT；没有则 none。

## 3. Authority / Reuse / Scope
- 生产权威与直接正式消费者：只列受影响者；非生产卡写不适用。
- 现有机制：写明应复用的能力或 reuse obligation；不得无故另建平行实现。
- Allowed Writes：精确文件或窄 glob，包含必要的新文件、测试和报告。
- Read-only / Out of Scope / Deferred：只列会影响施工边界的项目。

## 4. Execution Path
- 最小完整纵切及必要的安全顺序。普通实现不预写逐行操作；遇到关键新事实再停。

## 5. Required Validation
- Fast：精确入口、接受条件；必要时加 Direct。
- Catalog / Full：只在风险触发时写明原因；高成本验证写墙钟、内存、产物预算。
- 所列验证必跑；新发现直接回归允许最小定向检查，不得静默替换必跑命令。

## 6. Stop / Routing
- NEEDS_REPLAN：决定、范围、成功条件或风险边界发生实质冲突，报告事实与最小影响。
- BLOCKED：外部来源、权限、环境或必需验证无法完成，报告具体阻断。
- 需要用户作新产品/架构选择时停止并交 PLAN/协调器，不由 EXEC 自行决定。

## 7. Delivery
- 复用工作流现有 DELIVERY_CHECK：范围、必跑验证、计划一致性；不另写审核清单。
- 交付指向 changed paths、验证结果、Final HEAD、PR/branch、必要报告和 deferred 的权威位置。
- 按任务授权 commit/push/更新 PR；不 merge、不改 checklist、不自行进入下一卡。
```

按需追加条件模块：来源/Catalog 写权威分母、分区与追溯；Runtime/Mutation 写 producer、admission、
提交路径和失败 state unchanged；RNG/Event 写身份与消费顺序；公共迁移写正式调用者和旧路径处置；
既有 PR 接管写 PR URL、原 branch/base、绑定 HEAD，禁止替代 PR、rebase 和 force-push。
既有 PR 的 HEAD 漂移先停止并核对；只有改变批准事实或范围才 NEEDS_REPLAN。

卡片长度应由风险决定，不以字数表示严谨。能由稳定架构文档、任务账本和本协议得到的内容不要重复写进卡片。
