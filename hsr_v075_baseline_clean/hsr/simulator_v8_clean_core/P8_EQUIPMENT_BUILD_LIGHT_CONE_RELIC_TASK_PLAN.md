# P8 光锥、遗器与角色构筑装配任务计划

本文档面向没有前序会话上下文的新执行线程。它定义 P8 的完整目标、严格执行顺序、阶段边界和验收口径。P8 要把 P4 留下的装备边界声明替换为真正可执行、可审计、可扩展的装备与构筑体系，并接通当前 TBGD 中已发布光锥、遗器和套装效果。

P8 不是在角色卡中增加几个装备字段，也不是把最终面板交给 UI 手工填写。正确结构是：角色卡、光锥卡和遗器卡是彼此独立的内容来源；玩家构筑描述具体选择；构筑装配器校验并组合这些来源；战斗内核只执行装配完成后的通用属性、状态、监听、公式和事件机制。

```text
角色卡 ─────────┐
光锥卡 ─────────┤
遗器卡 ─────────┤→ 角色构筑装配器 → 已装配战斗单位 → Combat Core
玩家构筑输入 ────┘
```

P8 完成后，“这名角色装备了什么”和“这些装备产生了什么效果”必须同时可回答：前者来自构筑输入，后者来自 TBGD-first 的结构化装备卡、装配结果和通用战斗机制。任何装备效果都不能靠角色名、装备名、固定 ID、技能文本或 UI 计算进入内核。

## 使用方式

本文档只有最后一节是唯一可打标 checklist。背景、数据观察、问题总账、阶段目标和验收说明都不是第二套清单。

### S5-S21 与 R1-R2 直接执行入口

`P8-S0` 至 `P8-S4` 保留本文档中的阶段目标和既有验收记录。`P8-S5` 至 `P8-S21` 以及 S8 后新增的 `P8-R1`、`P8-R2` 修复门，均已由规划线程预先拆成单阶段执行卡，统一入口为：

```text
docs/p8_execution_cards/README.md
```

从 `P8-S5` 开始，执行线程不得只凭本文档中的阶段摘要自行展开实现，也不再临时重写一份执行卡。正确流程是：

1. 确认对应前置阶段已经验收并形成 Git 检查点。
2. 读取执行卡索引和当前阶段的唯一执行卡。
3. 只读核对卡内事实与当前代码；轻微事实变化写入报告，若变化影响目标、职责或验收谓词则停止并交回规划线程修订卡片。
4. 一次只实施一张卡，达到 `ready_for_review` 后立即停止，不提前进入下一阶段。

本文档负责 P8 总目标、全局红线、阶段依赖和唯一 checklist；单阶段执行卡负责当前阶段的具体目标、验收谓词、拟改范围和验证预算。两者出现实质冲突时，执行线程不得自行选择其中一套，应停止实施并由规划线程原子修订总计划与执行卡。

除第 7.1 节明确允许的双 worktree 分轨外，执行线程必须按 `P8-S0` 至 `P8-S21` 及 `P8-R1`、`P8-R2` 修复门组成的依赖图工作。后续阶段只能作为依赖背景，不能提前实现、提前出报告或混入当前阶段 evidence。

执行线程最多只能提交 `ready_for_review`，不能自称 `done`，不能修改本文档最后的 checklist。验收线程必须阅读真实代码、复核结构化矩阵、运行本阶段最小验证，并检查通用性、来源边界、扩展性和负例，验收通过后才勾选阶段并建立代码检查点。纯文档调整不要求单独提交检查点。

若一个阶段实际范围仍然过大，执行线程应先在执行卡中提出更细的内部批次和证据合并方式，不得自行降低目标、只挑简单样例或用一个宽泛聚合脚本冒充完成。

## 0. 前因后果

P4 在角色卡契约中留下了“光锥和遗器来自外部装备卡”的边界说明，并验证没有装备输入时 runtime 不会凭空产生装备效果。这在 P4 当时可以防止职责污染，但它不是正式扩展接口：

- `CharacterDataCardIR.card_contract` 中只有字符串式边界声明。
- Canonical IR 没有独立光锥卡、遗器卡、套装效果卡或构筑装配结果。
- `UnitSpec` 没有正式装备构筑输入，角色面板仍主要由调用者直接提供。
- RuleBook 没有装备查询面，ScenarioStateBuilder 不消费装备。
- P4 的装备验证明确是 `boundary_only`，只证明“不输入就不生效”，没有证明“输入后可以正确装配”。
- 当前 lowering 只把 `RelicSetSkillConfig` 当作宽泛实体表的一部分，而且保留字段与当前 raw 表并不完整对应；光锥配置、成长、叠影、遗器模板、主副词条和装备能力图均未形成正式 IR。

P7 已把 transition、原子提交、状态概率、伤害、护盾、随机、召唤和波次等内核语义回正到可继续扩展的状态。现在引入装备体系有两个目的：

1. 让模拟器能够从真实角色构筑形成正确战斗面板和装备被动。
2. 用大量真实装备机制压力测试内容卡、公式、状态、监听、资源、目标和行动系统，发现仍未接通的底层执行图，而不是在 UI 中掩盖缺口。
3. 在通用体系闭合后，用现有希儿卡、《于夜色中》、四件“繁星璀璨的天才”和两件“繁星竞技场”建立一个完整构筑纵切，证明角色、装备、词条、套装、战斗、审计和 replay 确实能通过同一条正式链路协作。

## 1. 当前数据事实基线

以下数字是 2026-07-13 对当前工作区数据的观察，用于帮助执行线程理解规模，不得作为固定数量写进 runtime 或未来验证。正式 evidence 必须根据本次 source fingerprint 重新计算。

### 1.1 光锥来源

当前主要来源包括：

- `ExcelOutput/EquipmentConfig.json`：光锥身份、稀有度、战斗命途、最大晋阶、最大叠影和技能引用。
- `ExcelOutput/EquipmentPromotionConfig.json`：每个光锥各晋阶阶段的等级上限、基础生命、基础攻击、基础防御及每级成长。
- `ExcelOutput/EquipmentSkillConfig.json`：每个叠影等级的参数、静态属性和能力名。
- `Config/ConfigAbility/Equip/*.json`：光锥及遗器套装的实际能力、modifier、callback、condition 和 task 图。
- `ItemConfigEquipment.json`、TextMap 等展示数据只用于内容卡展示和审计，不得进入 runtime 规则判断。

当前数据观察：

- 有 162 个已发布光锥；每个都有 7 条晋阶记录和 5 条叠影技能记录。
- 当前数据中出现 9 种内部战斗命途标识，因此禁止写死旧攻略常见的“七命途”枚举。
- 162 个能力名都能在 `ConfigAbility/Equip` 目录的多个文件中找到；不能只扫描历史总文件 `EquipmemtAbility.json`，也不能按版本文件名写死列表。
- 能力图中实际出现状态、属性、条件、动态值、伤害修正、资源、治疗、行动延后、目标变换和随机等多类机制，不能把光锥被动简化为面板加成。

### 1.2 遗器来源

当前主要来源包括：

- `ExcelOutput/RelicConfig.json`：遗器模板、套装、部位、稀有度、主副词条分组、等级上限和模式。
- `ExcelOutput/RelicBaseType.json`：六个实际部位允许的主词条种类。
- `ExcelOutput/RelicMainAffixConfig.json`：主词条在具体分组内的基础值和每级成长。
- `ExcelOutput/RelicSubAffixConfig.json`：副词条分组、基础值、步进值和每次 roll 的步进范围。
- `ExcelOutput/RelicSetConfig.json`：套装身份和激活档位。
- `ExcelOutput/RelicSetSkillConfig.json`：每个套装档位的静态属性、动态能力和参数。
- `Config/ConfigAbility/Equip/RelicAbility.json` 及同目录其他能力文件：套装动态效果的能力图。

当前数据观察：

- 六个实际部位是头部、手部、躯干、脚部、位面球和连结绳。`RelicBaseType` 还有一条没有部位标识的全量筛选记录，不能误判为第七个装备槽。
- 当前有 726 条遗器模板，其中 720 条是普通模式，6 条是特殊定制模式。特殊模式必须独立分类，不能套用普通模板后静默放行。
- 当前有 58 套已发布套装：32 套覆盖头、手、躯干、脚四个外圈部位并提供二件 / 四件效果；26 套覆盖位面球、连结绳两个内圈部位并提供二件效果。
- 当前有 117 条主词条定义、48 条副词条定义和 90 条套装档位效果。
- 90 条套装效果中，62 条引用动态能力，56 条含静态属性，其中 28 条同时包含两者。静态属性和动态能力都必须激活，不能二选一，也不能重复应用。

### 1.3 六部位主词条限制

当前 TBGD 的部位表表达了以下合法池：

| 部位 | 当前允许主词条 |
|---|---|
| 头部 | 固定生命值 |
| 手部 | 固定攻击力 |
| 躯干 | 生命百分比、攻击百分比、防御百分比、暴击率、暴击伤害、治疗量、效果命中 |
| 脚部 | 生命百分比、攻击百分比、防御百分比、速度 |
| 位面球 | 生命百分比、攻击百分比、防御百分比、七种属性伤害提高 |
| 连结绳 | 生命百分比、攻击百分比、防御百分比、击破特攻、能量恢复效率 |

正式实现必须从部位表、遗器模板的主词条分组和主词条定义三者交叉验证，不能只复制这张文字表。特殊定制模板只能使用自身分组允许的主词条，不能借普通部位池扩大选择。

### 1.4 副词条最终值语义

当前副词条分组包含固定生命、固定攻击、固定防御、生命百分比、攻击百分比、防御百分比、速度、暴击率、暴击伤害、效果命中、效果抵抗和击破特攻。

TBGD 提供每种副词条的基础值、步进值和单次步进上限。正式构筑输入表达一个已经完成的确定性遗器实例，而不是模拟刷取或强化过程：

- 主词条由模板分组、主词条 ID 和强化等级确定。
- 每条副词条只保留词条 ID、成品 `count` 和累计 `step`，用于从结构化定义计算最终值；二者不是养成历史记录。
- 同一遗器最多四种不同副词条。
- 副词条不能和主词条是同一属性，不能重复出现同一属性。
- 单条累计 step 必须位于该定义和 count 决定的范围内。
- 不检查初始副词条数量、每三级新增/强化节点、整件总 roll 预算或生成历史。
- 数值内部保留完整精度，显示舍入只能发生在 UI view model。

养成规则不属于战斗模拟输入边界，不建立 engine convention，也不作为遗器装配阻断条件。

### 1.5 外部资料的使用边界

外部资料只用于发现语义、交叉核对和选择实际例子，不是 v8 runtime 的规则来源：

- [Light Cone - Honkai: Star Rail Wiki](https://honkai-star-rail.fandom.com/wiki/Light_Cone)：核对光锥基础属性、对应命途被动和叠影 I-V。
- [Light Cones - Prydwen](https://www.prydwen.gg/star-rail/guides/light-cones)：核对不同命途仍可装备、基础属性仍生效、被动不生效的语义及实际光锥例子。
- [Relic Stats - Honkai: Star Rail Wiki](https://honkai-star-rail.fandom.com/wiki/Relic/Stats)：仅交叉核对部位主词条与副词条属性去重；掉落和强化过程不进入模拟器。
- [Relics - Prydwen](https://www.prydwen.gg/star-rail/guides/relics)：核对六部位、外圈二 / 四件套、内圈二件套和实际动态套装例子。
- [Theorycrafting General Mechanics - HoYoLAB](https://www.hoyolab.com/article/25247883)：辅助核对角色基础属性与光锥基础属性先合并，再应用百分比和固定值的面板公式。
- [Seele Guide - KeqingMains](https://hsr.keqingmains.com/seele/)：交叉核对希儿使用《于夜色中》、四件“繁星璀璨的天才”和“繁星竞技场”时的主词条、副词条优先级及速度取舍。
- [Seele Best Builds and Teams - Game8](https://game8.co/games/Honkai-Star-Rail/archives/405758)：交叉核对指定 4+2 组合、攻击鞋、量子伤害球、攻击绳以及繁星竞技场暴击门槛的实际配装建议。
- [Seele Best Build Guide - Prydwen](https://www.prydwen.gg/star-rail/characters/seele)：交叉核对当前版本常用的暴击、攻击和速度目标区间。攻略只用于选择示例构筑，不是属性公式或装备效果的 runtime 来源。

当外部资料和当前 TBGD 冲突时，必须先审查版本差异、lowering 和检查谓词。外部旧资料声称的固定数量、名称或规则不得覆盖当前数据。例如当前 TBGD 已有 9 种命途，不能采用旧资料的固定七命途模型。

## 2. 目标架构

P8 要建立四类互相分离的对象和职责。

### 2.1 装备定义

装备定义来自 TBGD，经 lowering 进入 Canonical IR：

- 光锥定义描述身份、命途、稀有度、成长曲线、叠影参数、静态效果和能力图引用。
- 遗器模板描述套装、部位、稀有度、主副词条分组、等级上限和特殊模式。
- 套装定义描述当前数据声明的激活门槛，以及每个门槛对应的静态属性和动态能力。
- 主副词条定义描述属性类型和精确数值计算所需参数。

装备定义是角色卡的同级内容来源，不嵌入任何具体角色卡，也不包含玩家拥有的具体实例。

### 2.2 玩家构筑输入

玩家构筑输入属于 scenario / build configuration，描述本次战斗选择：

- 角色等级、晋阶、星魂和启用的行迹等角色构筑信息。
- 可选的一件光锥实例，包括光锥身份、等级、晋阶、叠影和实例身份。
- 零至六件遗器实例，包括模板、槽位、强化等级、主词条、副词条 roll 和实例身份。

玩家构筑输入是事实选择，不是规则结果。UI 可以提交“我选择了这些装备”，不能提交“所以最终攻击力是某个数”来绕过装配器。

### 2.3 构筑装配器

构筑装配器位于 L2 内容装配层，负责：

- 校验所有引用、范围、槽位、命途、词条和套装关系。
- 从角色、光锥和遗器来源计算基础属性与静态贡献。
- 统计满足的套装档位。
- 选择并参数化应启用的装备机制。
- 生成稳定、不可变、可指纹化的装配结果和来源贡献账本。
- 对缺来源、非法输入和未准入 gameplay ability 给出结构化 blocked，不生成半成品战斗单位。

构筑装配器不能执行回合、状态、伤害、资源或行动规则；它只把已选择的机制和参数交给通用系统。

### 2.4 战斗运行时

runtime 只消费装配结果：

- 最终基础面板和战斗前静态属性已经有明确贡献来源。
- 光锥和套装动态效果以通用 ability / modifier / callback / condition / effect 图接入。
- 战斗开始后构筑不可被普通 action command 修改。
- runtime 不读取原始装备表、TextMap、装备名称、技能描述或玩家输入的最终面板答案。

## 3. P8 总目标

P8 完成后，系统必须具备以下能力：

- 当前已发布光锥、遗器模板、主副词条、套装档位和装备能力都有结构化来源清单和唯一引用关系。
- 角色、光锥、遗器和构筑是不同对象；旧字符串式装备边界不再冒充正式接口。
- 正式角色 scenario 能从角色等级 / 晋阶和构筑输入生成基础面板，不需要 UI 手填最终生命、攻击、防御和速度。
- 光锥等级、晋阶和叠影均由数据决定；基础生命、攻击、防御精确计算，叠影只改变对应被动参数。
- 任意命途角色可以装配光锥；命途不匹配时保留光锥基础属性，但不激活光锥静态被动和动态能力，并有明确装配决策记录。
- 六个遗器槽位、外圈四件与内圈两件的域边界得到强校验；同一角色不能出现重复槽位，同一实例不能被队伍重复装备。
- 每个部位的主词条只能来自其真实合法池，数值按模板分组和强化等级计算。
- 每条副词条都由真实分组和 count/step 表达计算，满足最多四条、不重复、不与主词条相同且单项范围合法。
- 外圈支持四件同套、二加二、二件加散件和全散件；内圈支持同套二件或不成套。达到四件门槛时同时激活同套二件和四件效果。
- 套装档位从数据读取，不以 `2/4`、SetID 范围或文件名作为长期硬编码；当前 4+2 规则是数据驱动结果。
- 静态属性、条件属性和动态能力不会漏算或重复算，完整精度进入 runtime，显示舍入留在 UI。
- 装备动态效果通过现有通用内核执行，并覆盖当前已发布装备实际使用的 gameplay opcode、condition、target、event 和 dynamic binding。
- 每项最终属性和每个动态效果都能追溯到具体角色来源、光锥实例、遗器实例或套装档位。
- snapshot / replay 使用稳定构筑指纹和来源清单；推演器紧凑状态不重复携带大体积静态装备定义。
- UI / API 可以查询装备目录、合法输入、装配结果和 blocked reason，但不自行计算词条、套装、命途被动或最终面板。
- 现有希儿示例卡可以通过正式构筑接口装配《于夜色中》、四件“繁星璀璨的天才”和两件“繁星竞技场”，形成一套词条合法、阈值明确、可实际执行动作并可完整 replay 的参考构筑。

## 4. P8 明确不做

- 不实现遗器掉落概率、刷取、合成、分解、强化材料消耗或背包管理。
- 不模拟“随机生成一件遗器”的 farming RNG。P8 消费确定的遗器实例，并验证该实例是否可能存在。
- 不制作 UI 页面布局；只提供 UI 可消费的结构化查询与装配结果。
- 不允许战斗中普通动作更换光锥或遗器。未来特殊玩法若允许换装，必须另立来源和生命周期计划。
- 不批量重做全角色技能、全怪物、关卡和环境机制；但为正确装配角色基础面板所必需的角色等级 / 晋阶输入属于 P8 前置范围。
- 不把外部攻略数值、角色推荐权重、遗器评分表或 `SpecialAvatarRelic*` 推荐数据当成战斗规则。
- 不实现自动配装、遗器评分或“最佳构筑”推荐器。希儿完整示例是版本化的 source-backed 参考输入，不代表唯一最优解，也不能替代全装备覆盖。
- 不保留会污染 v8 正式接口的旧装备 JSON 兼容层。工作区内测试 fixture 可以保留明确标记的 kernel-fixture 面板输入，但不得冒充正式 source-backed 构筑。

## 5. 全局红线

- 禁止在角色卡中复制光锥或遗器规则；角色卡只能通过构筑引用装配结果。
- 禁止以装备名、角色名、SetID 范围、固定装备 ID、固定能力名或固定当前数量驱动 runtime 和主验证。
- 固定 ID 如果确实来自某个装备能力中的结构化条件，只能留在该内容 IR 中，由通用条件系统解释，不能变成 core 特判。
- 禁止用 `card_contract` 字符串、空 slot、未来字段或报告文字声称装备接口已经完成。
- 禁止 UI / scenario 直接提交最终面板来绕过正式装配，并同时声称这是 source-backed 构筑。
- 禁止 runtime 读取 `EquipmentConfig`、`RelicConfig`、TextMap、原始 ability JSON 或技能文本。
- 禁止把不同命途光锥判为“无法装备”；当前语义是基础属性生效、光锥能力不激活。若当前 TBGD 后续出现明确例外，必须由结构化来源覆盖。
- 禁止把光锥基础属性和光锥被动属性混为一类。命途失配只关闭被动，不关闭基础生命、攻击和防御。
- 禁止从显示后的整数 / 百分比反推内部词条值；内部必须使用 TBGD 精度。
- 禁止允许遗器主词条超出部位池、重复槽位、重复副词条、主副同属性、超过四条副词条或单项 count/step 越界。
- 禁止按 SetID 数字段判断内外圈；必须依据模板部位和套装定义建立域关系。
- 禁止只统计“同套数量”而忽略槽位合法性。非法重复部位不能贡献套装计数。
- 禁止达到四件套后只启用四件效果而漏掉二件效果。
- 禁止把静态属性表和 ability 图中的效果互相替代；二者都存在时必须按各自来源执行，并用审计证明没有重复计入。
- 禁止 `SkillEquip`、套装参数或副词条数值在 runtime 临时查 raw；必须在 lowering / assembly 阶段形成类型化绑定。
- 缺少 gameplay ability、参数、目标、条件或事件源时，正式构筑必须 blocked，不能只跳过该装备效果后开始战斗。
- client-only、展示和动画 task 可以明确排除，但必须有结构化分类依据，不能把未知 gameplay task 伪装成 client-only。
- 通用覆盖验证必须以结构化谓词选样；具体装备和套装不能成为全量覆盖的通过条件。P8-S20 允许固定希儿及指定装备作为明确标记的端到端示例，但固定名称 / ID 只能存在于示例 manifest、示例验证和报告中，不能进入 compiler、assembly、runtime 或通用查询逻辑。
- P8 所有重验证串行运行，不默认写完整 Canonical IR、完整 RuleBook 或全量 transition dump。

## 6. 完成口径和缺口分类

每个来源项必须落入以下机器可读状态之一：

- `executable`：来源完整，已 lower，已装配，runtime 执行、settlement、source audit 和 replay 均通过。
- `non_gameplay`：结构化证据证明只影响客户端、动画、展示或养成成本，不进入战斗执行。
- `source_gap_blocked`：当前 raw 数据确实缺少完成该规则所需来源，正式构筑 blocked 且 state unchanged。
- `lowering_gap`：raw 有来源但没有完整投影到类型化 IR。
- `admission_gap`：IR 已存在但装配或 runtime 没有准入。
- `implementation_missing`：已有真实可执行来源，但通用内核不能正确执行。
- `validation_gap`：实现可能存在，但当前证据无法证明。

`P8-DONE` 使用严格口径：

- 当前 source fingerprint 下所有已发布光锥、普通玩家遗器模板、套装档位和 gameplay ability 均必须 executable。
- P8-S20 希儿完整构筑必须通过正式装配、场景出生、装备 provider 注册、来源审计和 replay；示例不得依赖手填最终面板、手填装备效果或 sample-only runtime 分支。角色动作图由角色卡内容阶段独立闭合，不得伪造为装备验收前置。
- 当前数据中的特殊定制遗器必须完成来源分类；若属于可进入战斗的构筑，也必须可执行，不能用“不是普通遗器”跳过。
- `lowering_gap`、`admission_gap`、`implementation_missing` 和 `validation_gap` 必须为零。
- 只允许真实 raw 缺源留下 `source_gap_blocked`，且必须证明不是扫描、lowering 或谓词过窄造成的误报。若该缺源会让某个已发布装备无法完整执行，则仍阻断 P8-DONE，除非验收线程确认该来源是纯展示 / 非 gameplay。
- “装备底座可用”不能替代 P8-DONE。若执行资源需要分批，可逐阶段验收，但最终 checklist 不得在全量 gameplay 覆盖前完成。

```text
验证命令：
  - 本阶段唯一主验证及它直接证明的目标。
  - 直接回归的触发条件；不得预列与实际 diff 无关的固定套餐。
  - 明确不跑的重聚合及理由。
  - 完整入口运行次数、累计墙钟、输出规模、RuleBook 构建次数和限峰值措施。
  - 失败后允许运行的切片，以及达到预算后必须暂停的条件。

ready_for_review evidence：
  - 代码 diff 摘要。
  - 目标到证据映射。
  - 当前 source fingerprint。
  - 结构化验证摘要和关键反例。
  - 尚未关闭的真实 blocker。
```

执行卡不得只复述阶段标题。涉及数值的阶段必须写出独立 oracle 来源和边界值；涉及全量覆盖的阶段必须写出当前总数如何动态获得、如何防空集合和如何证明没有漏扫文件。执行线程只能提交 `ready_for_review` evidence；卡内和总计划中的勾选项均由验收线程维护。

## 9. P8-S0 装备来源与机制基线

### 阶段目标

建立一份独立于旧 P4 报告的当前源码基线。完成后，后续线程能够准确回答：当前发布了哪些光锥和套装；每个配置引用的成长、叠影、主副词条和 ability 是否唯一存在；能力分布在哪些文件；有哪些 gameplay 机制族；哪些表只是展示、推荐、养成或特殊模式来源。

### 本阶段只做

- 单独列出普通遗器、特殊定制遗器、展示表、推荐权重表和疑似非 gameplay 来源。

### 本阶段不做

- 不新增正式装备 IR。
- 不修改 ScenarioStateBuilder 或战斗结果。
- 不把未知 opcode 提前标记为 non-gameplay。
- 不运行 P1-P7 全量聚合。

### 允许验收通过

- 六个真实部位与无部位筛选行被正确区分；普通与特殊遗器模式独立统计。
- 每个 gameplay / non-gameplay / unknown 分类都有原始路径、raw type 和判定依据。

### 不允许验收通过

### 最小证据与验证

- 新增 P8-S0 focused inventory 验证，仅读取约 3 MB 装备相关语料。
- 输出 source inventory、reference integrity、mechanism family、special-source classification 和 resource budget 五类摘要。
- 运行 `compileall` 与 `git diff --check`；不构建完整 RuleBook。

## 10. P8-S1 类型化装备与构筑架构

### 阶段目标

### 本阶段只做

### 允许验收通过

- 将装备规则直接复制进每张角色卡。
- 让 runtime 为了方便直接读取完整装备卡内部结构。
- 只有序列化 smoke，没有引用冲突和 blocked 负例。

### 最小证据与验证

- P8-S1 类型契约、RuleBook query、immutability 和缺引用负例验证。
- `compileall`、P6 架构静态边界的直接回归、`git diff --check`。
- 不构建全量 TBGD；使用小型类型 fixture 和 S0 摘要。

## 11. P8-S2 正式角色构筑输入与基础面板

### 本阶段只做

### 本阶段不做

- 不重做角色技能和专属资源。
- 不移除内核 fixture 所需的显式面板能力，但必须隔离模式和入口。
- 不允许用户设置初始行动值；正式时间线仍由最终速度和规则初始化。

### 允许验收通过

### 最小证据与验证

- P8-S2 角色基础构筑正负例和边界数值验证。
- P4 行迹 / 星魂装配、P6 出生边界、P7 时间线初始化的直接回归。

## 13. P8-S4 光锥实例、成长与命途激活决策

### 阶段目标

让玩家构筑可以选择一件确定光锥，并从等级、晋阶和叠影得到精确基础属性与明确被动激活决策。完成后，“能否装备”“基础属性是否生效”“被动是否激活”是三个分开的结果。

### 本阶段只做

- 建立光锥实例输入和实例身份，校验引用、等级、晋阶、叠影和当前卡片上限。
- 从对应晋阶记录计算当前等级的基础生命、攻击、防御，保留完整精度。
- 选择对应叠影等级的参数与静态属性定义。
- 比较角色战斗命途与光锥命途：任何角色可装配；基础属性始终贡献；命途不匹配时所有光锥被动保持 inactive。
- 记录激活 / 不激活原因及来源，不用异常文字代替机器状态。
- 队伍层面验证同一光锥实例身份不能重复装备。

### 本阶段不做

- 不应用静态被动属性。
- 不启动动态 ability。
- 不模拟升级材料或叠影消耗。
- 不按角色推荐判断是否允许装备。

### 允许验收通过

- 等级 1、各晋阶边界和最高等级的基础属性有来自 promotion rows 的独立计算 oracle。
- 叠影 I-V 选择正确参数，但不改变基础属性。
- 同命途样例标记被动可激活；不同命途样例保留相同基础属性并标记被动 inactive。
- 非法等级 / 晋阶组合、叠影 0 / 超上限、未知光锥和重复实例被拒绝。
- 数值计算不使用显示文本或固定观测答案。

### 不允许验收通过

- 命途不匹配时整件光锥失效。
- 命途不匹配时仍应用静态被动属性。
- 由 UI 计算并提交光锥三项基础数值。
- 在 runtime 按等级临时查询 promotion raw。

### 最小证据与验证

- P8-S4 光锥实例与成长边界验证，包含同 / 异命途成对样例。
- P8-S2 构筑输入直接回归、数值 round-trip、`compileall`、`git diff --check`。
- 不运行动态 ability 或全量战斗聚合。

## 14. P8-S5 光锥静态属性装配

### 阶段目标

将叠影记录中的静态被动属性接入统一属性贡献账本。完成后，光锥基础三维与光锥被动静态属性拥有不同来源、不同激活条件和不同面板位置，命途失配不会错误获得被动属性。

### 本阶段只做

- 将当前叠影的静态属性 lower / bind 为类型化贡献项。
- 仅在被动 activation 为 active 时将静态属性交给装配器。
- 区分基础生命 / 攻击 / 防御与生命百分比、攻击百分比、效果命中等被动属性。
- 记录光锥实例、叠影等级、技能行和属性项 source trace。
- 验证静态属性与后续 ability 图不会因同一 raw 项被重复装配。

### 本阶段不做

- 不执行条件属性、modifier 或 callback。
- 不实现遗器属性。

### 允许验收通过

- 同命途时静态属性按叠影档位进入账本；异命途时不进入，但基础三维仍存在。
- 每项贡献有唯一来源，不出现双计；缺属性类型或数值绑定时正式构筑 blocked。
- 无静态属性不是 gap，必须和 lowering 漏项区分。

### 不允许验收通过

- 用固定光锥 ID 作为主正例选择器。
- 把文本中的百分比人工填入属性贡献。
- 为方便 UI 同时保存“原贡献”和“已加总贡献”并在后续重复消费。

### 最小证据与验证

- P8-S5 静态属性来源分类矩阵、真实空集记录、命途失配负例、双计负例。
- P5 value binding、P8-S4 成长和 S2 属性账本直接回归。
- focused RuleBook 至多构建一次，不运行完整 equipment ability 图。

### 最小证据与验证

## 16. P8-S7 光锥属性、状态、条件与监听机制闭合

### 阶段目标

### 本阶段只做

### 不允许验收通过

- 每种机制只挑一件容易光锥后声称全族完成。
- 使用技能描述替代 raw condition。
- 用角色 / 光锥固定 ID 驱动主验证。

### 最小证据与验证

### 最小证据与验证

- 构筑 fingerprint 包含实例选择，但不包含 UI 展示名称。

### 本阶段不做

### 不允许验收通过

### 最小证据与验证

- S9 检查点默认继承；只有实际修改正式构筑 schema、队伍占用或共用实例查询时，才运行对应最小 direct，最多两项。
- 不计算属性，不运行战斗。

## 20. P8-S11 主词条合法池与精确数值

让每件遗器的主词条只能来自真实模板和部位允许的交集，并根据稀有度分组与强化等级计算完整精度数值。完成后，固定头部生命、固定手部攻击及身体 / 脚部 / 球 / 绳的不同池都由数据驱动验证。

### 本阶段只做

- 解析部位合法属性池、模板 MainAffixGroup 和主词条定义的关系。
- 用主词条基础值与每级成长计算当前强化等级数值。
- 对普通和特殊模板分别按自身 group admission。
- 保留 raw property、group、affix ID、level 和数值来源。
- 为全部六部位建立按结构谓词选择的合法 / 非法属性矩阵。

### 本阶段不做

- 不按主词条掉落概率生成遗器。
- 不处理副词条。
- 不应用到最终面板。

### 允许验收通过

- 六个部位的当前合法池由 raw 表交叉得到，与 S0 / 外部语义对照一致。
- +0、一个中间等级和最大等级数值有独立 oracle，使用完整精度。
- 头部非固定生命、手部非固定攻击、脚部暴击、球部能量恢复、绳部元素伤害等非法组合被拒绝。

### 不允许验收通过

- 接受用户直接提交主词条最终数值。
- 使用 UI 四舍五入后的百分比作为内部值。
- 只测六个合法正例，不测跨槽错误。

### 最小证据与验证

- focused pure calculation，无完整 RuleBook。

- `compileall`、`git diff --check`。

## 21. P8-S12 副词条最终值、精度与约束

### 阶段目标

建立能够表达自定义成品遗器的副词条模型。完成后，每条副词条数值由 affix 定义、累计 count 和累计 step 计算；整个遗器满足正确分组、属性去重、主副排斥、最多四条和单项数值范围。本阶段只完成词条 admission；在 S13 套装统计和 S14 静态贡献完成前，非空遗器构筑必须保持 battle blocked，不能以零遗器效果进入正式战斗。

### 本阶段只做

- 从 SubAffixGroup 选择合法副词条定义。
- 定义并计算 `affix + count + step` 语义，验证 step 范围与整数性。
- 内核保留完整小数精度；显示投影由 UI/view model 负责，验证其结果不会回流内核。
- 强制同一遗器副词条属性唯一，且不与主词条 raw property 相同。
- 校验单条 `count > 0` 且 `0 <= step <= count * StepNum`。

### 本阶段不做

- 不生成随机副词条。
- 不模拟或验证初始词条数量、每三级新增/强化、总 roll 预算和养成历史。
- 不实现强化材料和概率权重。
- 不按角色推荐判断词条好坏。
- 不应用到最终面板。

### 允许验收通过

- 当前各稀有度副词条分组都有 low / mid / high step 数值 oracle。
- 合法 0-4 条副词条和各单项 count/step 边界样例通过。
- 重复 affix、不同 affix 但同 property、主副同 property、第五条、count 非正和单条 step 越界均被拒绝。
- 固定生命与生命百分比被视为不同 property，可在符合其他约束时共存。
- 即使 UI 投影后显示相同，内部不同的 roll 仍保持不同完整值和 fingerprint；内核不定义舍入方式。
- 四条副词条分别达到各自合法上界时仍可作为自定义成品构筑使用，不要求还原强化历史。
- 合法遗器形成只读 selection，并为每件 selection 保留一条 S13/S14 后续 blocker；空遗器构筑不受影响。

### 不允许验收通过

- 只接收用户提交的最终副词条浮点值。
- 只检查最多四条，不检查每条副词条自身的来源、属性和数值范围。
- 副词条通过后直接标记 battle admitted，导致尚未入账的遗器以零效果进入战斗。
- 因外部 API 使用 count / step 就把第三方 API 当规则事实来源。
- 将遗器评分或推荐权重混入合法性判断。

### 最小证据与验证

- P8-S12 pure sub-affix calculator、独立 raw oracle、单项边界、非法组合和外部显示投影隔离。
- 复用一次受预算约束的 relic domain catalog，并在唯一 RuleBook 构建前选择引用闭合的词条定义；不构建完整 Canonical IR 或完整 RuleBook。
- `compileall`、`git diff --check`。

## 22. P8-S13 外圈四槽、内圈两槽与套装档位

### 阶段目标

从已经通过槽位和词条校验的遗器实例统计套装，正确表达外圈四槽与内圈两槽。完成后，四件同套会同时激活二件和四件档位；外圈二加二会激活两个二件档位；内圈只有同套两件才激活对应二件档位；散件和跨套不产生不存在的效果。

- 生成激活档位清单、未满足档位和来源实例列表。

### 本阶段不做

- 不启动套装 ability。
- 不允许非法重复槽位参与计数。

### 允许验收通过

- 4+2 满配、外圈二加二、外圈四件同套和内圈错配均有独立正反例。
- 四件同套激活同套二件与四件两条独立来源记录。
- 两个不同外圈二件套分别激活，不被合并成任一四件套。
- 内外圈域不会互相补数；域关系不依赖 SetID 范围。

### 不允许验收通过

- 只支持固定“一个四件套 + 一个二件套”，不支持二加二。
- 四件套只激活四件效果。
- 先按 set 数量激活，再发现槽位非法。
- 将当前 2 / 4 写死在 core 而不读取套装定义。

### 最小证据与验证

- P8-S13 set activation matrix，覆盖所有组合类别和非法槽位 no-contribution。
- S9-S12 检查点默认继承；只有实际修改实例准入、身份或套装定义查询时，才运行一个对应最小 direct。
- pure assembly 测试，不运行动态能力。

## 23. P8-S14 遗器与套装静态属性装配

### 阶段目标

### 本阶段只做

- 处理套装同时含 PropertyList 与 AbilityName 的情况：静态部分现在装配，动态部分保留给 S15。
- 按实例、affix、套装档位记录贡献来源和 activation evidence。
- 防止同一 row 因 entity lowering 与正式装备 lowering 重复进入账本。

### 本阶段不做

- 不执行套装动态 ability。
- 不最终冻结角色面板顺序，跨角色 / 光锥 / 遗器综合收口在 S18。
- 不使用推荐权重表调整属性。

### 不允许验收通过

### 最小证据与验证

## 27. P8-S18 统一最终面板与战斗出生顺序

### 阶段目标

把角色自身、光锥基础属性、行迹、光锥被动、遗器主副词条和套装静态属性统一装配为正式战斗面板，并在面板完成后注册动态装备机制。完成后，战斗单位出生、入场事件和时间线初始化的顺序稳定，不会因调用位置不同得到不同结果。

### 本阶段只做

- 定义并实现统一贡献求值顺序：角色与光锥基础生命 / 攻击 / 防御先形成共同 base；百分比贡献作用于 base；固定贡献最后加入；速度使用角色基础速度、速度百分比和固定速度；其他属性按类型化聚合规则处理。
- 将行迹、光锥、遗器和套装静态贡献纳入同一 ledger，而不是多个系统各自修改 UnitState。
- 用装配结果生成正式 playable-character birth / setup 输入，runtime 不重新理解构筑。
- 先完成静态面板和资源，再注册装备 ability，再派发 OnStart / OnEnterBattle，再初始化依赖最终速度的时间线。
- 初始当前生命、能量、行动值等由正式规则基于最终面板计算；UI 不直接配置派生值。
- 检查 summons / servants 读取 owner 属性的时机和来源，不无条件继承装备。

### 本阶段不做

- 不重写全部 UnitBirthTemplateIR 用途；如需扩展统一出生边界，执行卡必须证明和 P6 的关系。
- 不实现 UI。
- 不允许战斗中改构筑。

### 允许验收通过

- 生命、攻击、防御和速度各有独立公式 oracle，覆盖基础、百分比、固定值和多来源组合。
- 同一构筑无论输入顺序如何都生成相同 fingerprint、ledger 和最终面板。
- 移除光锥、改变叠影、替换一件遗器或改变套装门槛只影响对应贡献和机制。
- OnEnterBattle 条件读取最终面板；时间线读取最终速度；startup 不重复应用静态值。
- 正式场景不接受 UI 提交的最终面板或初始行动值覆盖。
- 缺任何选中 gameplay 机制时不生成可开战的半成品 unit。

### 不允许验收通过

- 在 ScenarioStateBuilder 中按来源顺序逐次修改 attack / hp，导致顺序相关。
- 把光锥基础攻击当固定攻击放到百分比之后。
- 将遗器固定攻击计入 base attack。
- 在最终速度完成前初始化行动条。
- 为兼容旧 fixture 让正式 build 默默接受 panel override。

### 最小证据与验证

- P8-S18 final panel formula、input permutation、startup order 和 blocked birth 验证。
- S2、S5、S14、P4、P6、P7 检查点默认继承；只按实际修改的共享最终面板、出生、时间线或事件边界选择最小 direct，最多两项。
- 本阶段只构建一次受控装备 RuleBook；不重跑光锥轨或遗器轨聚合，所有重验证串行并输出 `/tmp`。

## 28. P8-S19 查询、审计、snapshot、replay 与紧凑状态

### 阶段目标

让 UI、场景编辑器和未来推演器能够安全消费装备体系，同时保持规则只在 core / assembly。完成后，外部层可以查询装备目录、合法槽位和词条、提交构筑、读取装配结果与 blocked reason；snapshot / replay 能锁定构筑身份；推演器状态不复制完整装备定义。

### 本阶段只做

- 提供只读光锥目录、遗器模板 / 套装目录、部位合法主词条和构筑校验接口。
- 提供装配结果摘要：最终面板、静态贡献、已激活 / 未激活能力、套装档位和 blocked reason。
- UI 查询返回规则结果，不要求 UI 统计套装、计算词条或判断命途被动。
- snapshot / replay 保存构筑 manifest / fingerprint 的稳定引用，并验证源码 / IR 指纹一致性。
- 推演器 compact state 只保留影响战斗分支的构筑身份和当前动态状态，完整 provenance 按需查询。
- source audit 支持从面板 term / mutation 回到实例、装备卡、IR 和 TBGD。

### 本阶段不做

- 不制作 UI 布局或交互视觉。
- 不让推演器在战斗中搜索装备组合；P8 构筑在开战前固定。
- 不把完整装备 JSON 复制进每个 BattleState。

### 允许验收通过

- 查询接口幂等、只读，不触发 startup、事件或时间线推进。
- UI 只提交选择，非法构筑由装配器返回结构化错误。
- 同一构筑 replay 得到相同装配结果和 transition；源码指纹 / manifest 被替换时拒绝精确回放。
- compact state 大小不随完整装备目录规模线性增长。
- 静态贡献和动态 mutation 都能完成来源 walkback。
- 查询缺字段、伪 fingerprint、陈旧 manifest、UI 预计算最终面板和篡改 ledger 负例被拒绝。

### 不允许验收通过

- UI 根据当前六件遗器自行激活套装。
- API 接收“套装已激活”“光锥被动已启用”作为可信输入。
- replay 只比较最终面板，不验证构筑来源。
- 为方便审计把所有 raw source 放进推演器哈希状态。

### 最小证据与验证

- P8-S19 query purity、build round trip、source walkback、stale fingerprint 和 compact-state budget 验证。
- P7 查询、replay 和 compact-state 检查点默认继承；只有实际修改对应共享模块时才运行最小 direct，最多两项。
- 不需要重新跑全部 equipment ability transition，复用当前指纹绑定的 S8、R1 与 S17 摘要。

## 29. P8-S20 希儿完整装备构筑纵切

### 阶段目标

通过与未来 UI / 推演器相同的正式构筑接口，把现有希儿示例卡、80 级叠影 1 的《于夜色中》、四件五星“繁星璀璨的天才”和两件五星“繁星竞技场”装配成一个可直接进入战斗的完整实例。完成后，这个实例必须同时证明角色基础面板、光锥成长与被动、六件遗器主副词条、外圈四件套、内圈两件套、条件阈值、正式出生、来源审计和 replay 可以在同一条真实链路上协作。希儿普攻、战技和终结技的完整动作图属于后续角色卡内容闭合，不是装备阶段完成条件。

该阶段是端到端可用性纵切，不是手工制作三个只服务希儿的特殊内容卡。光锥卡、遗器模板卡和套装卡必须来自 S3-S17 已建立的通用 lowering；希儿构筑只是选择这些定义并提供六个合法实例。示例通过也不能替代 S21 的全装备 coverage。

### 示例构筑基线

示例采用当前工作区已有的希儿内容卡，并使用以下版本化构筑选择：

| 构筑项 | 示例选择 | 选择目的 |
|---|---|---|
| 角色 | 现有希儿示例卡，80 级、E0；不选择尚未准入的角色行迹或技能等级节点 | 复用真实角色构筑和正式出生边界，不用“默认满级”伪造角色卡闭合 |
| 光锥 | 《于夜色中》，80 级、晋阶 6、叠影 1 | 同时覆盖光锥基础属性、常驻暴击率和随当前速度变化的分档被动 |
| 外圈 | 五星“繁星璀璨的天才”头、手、躯干、脚各一件，全部强化至 15 级 | 覆盖固定主词条、可选主词条、量子伤害和按敌方弱点分支的防御无视 |
| 内圈 | 五星“繁星竞技场”位面球、连结绳各一件，全部强化至 15 级 | 覆盖暴击率静态贡献以及达到门槛后的普攻 / 战技伤害条件 |

主词条固定为：躯干暴击率、脚部攻击百分比、位面球量子伤害、连结绳攻击百分比；头部和手部使用其唯一合法主词条。选择暴击率躯干是为了让示例稳定越过“繁星竞技场”的当前暴击门槛，而不是宣称所有希儿构筑都必须使用暴击率躯干。

副词条必须由当前五星副词条表中的真实词条和成品 count / step 组成，不得直接填写最终百分比。项目只模拟完成养成后的遗器输入，不还原初始词条、强化次数或每三级强化历史。整体优先级为暴击率 / 暴击伤害、攻击百分比、速度，再按部位主副词条排斥选择固定攻击或其他合法补位。六件实例至少满足：

- 每件恰好一个合法主词条、至多四种不同副词条，主副不重复且每条 count/step 独立合法。
- 静态装配后的暴击率达到“繁星竞技场”当前来源声明的激活门槛，并以 75%-85% 作为本示例的配装目标；暴击伤害至少 160%，战斗外攻击力至少 2900。目标来自攻略交叉对照，最终值仍必须由真实 roll 和装配公式计算，不允许反填答案。
- 使用攻击鞋，不为追求《于夜色中》满档牺牲主要攻击和暴击词条。
- 速度副词条形成可审计的战斗外速度；《于夜色中》的分档必须在受控 runtime 当前速度切片中从 IR 参数动态计算，不得在 runtime 写死，也不得用角色动作 fixture 冒充战技速度变化。

具体六件副词条分配、每条 count 和累计步进必须在阶段执行卡中列成 source-backed manifest。执行线程可以在单项合法范围内调整分配以满足上述整体目标，但必须解释调整原因；不能把攻略中的最终面板当作输入。

### 本阶段只做

- 建立一份可机器读取、可版本化、可通过正式 API 导入的希儿完整构筑参考卡 / example manifest；它只引用各内容卡和实例输入，不复制装备规则。
- 证明 preset 引用的角色、光锥、六件遗器模板、主副词条和套装档位都由当前 RuleBook 查询得到，而不是示例文件复制规则。
- 输出装配贡献账本，逐项列出角色、光锥基础属性、光锥静态被动、行迹、六件主词条、全部副词条和两个套装的贡献。
- 验证《于夜色中》在多个受控 runtime 当前速度下的实际档位变化；档位必须从当前速度和光锥参数计算，切片不得冒充角色动作闭合。
- 验证“繁星竞技场”在暴击率达到 / 未达到门槛时的启用与关闭，静态暴击率和条件伤害必须分开审计。
- 验证“繁星璀璨的天才”二件效果、四件基础防御无视和敌方具有量子弱点时的额外分支。
- 通过正式场景构建和 provider 注册生成战斗初态，不借用 kernel fixture 或验证专用角色动作入口。
- 对 provider 注册和受控装备条件 transition 做 snapshot / replay，并完成至少一条面板 term，以及《于夜色中》、繁星竞技场和量子套各一条动态 condition decision 的全来源反查；不能强求本来只影响公式的机制伪造状态 mutation。
- 提供由同一 manifest 派生的受控反例：暴击率降至门槛以下、拆掉一件外圈、拆掉一件内圈、敌人无量子弱点。反例只能改变对应效果，不能污染其余来源。

### 本阶段不做

- 不做自动配装、词条评分、伤害最大化搜索或角色攻略系统。
- 不把该 preset 注册为希儿的内核默认装备；scenario 未选择时不得自动装配。
- 不为示例手工创建《于夜色中》、遗器或套装的 sample-only IR。
- 不为了得到攻略面板而修改角色卡、装备公式或通用结算顺序。
- 不在本阶段重复运行全装备聚合；S21 负责证明示例之外的完整覆盖。

### 允许验收通过

- 示例通过与正式场景相同的构筑输入、装配、出生、provider 注册、查询和 transition 接口完成；删除示例文件不会改变任何 core 行为。
- 固定角色 / 装备 ID 只出现在 example manifest、focused 示例验证和报告中；compiler、RuleBook、assembly、runtime 和通用验证选择均没有希儿或该套装特判。
- 六件遗器全部是当前 TBGD 中真实存在的五星模板，槽位为严格四外圈加两内圈；每个主副词条和 roll 均可由定义独立重算。
- 最终面板由贡献账本逐项求和得到，暴击门槛、速度档位和两个套装效果均由 runtime 当前值触发，不由 preset 声明“已激活”。
- 装备条件切片能区分《于夜色中》、繁星竞技场和量子套的适用范围；敌方弱点分支、速度变化和暴击门槛反例均符合来源语义，且不宣称希儿动作图已经闭合。
- 构筑 fingerprint、snapshot、transition、settlement 和 replay 一致；从动态结算 term / condition decision 可以回到具体光锥或套装档位，从静态 term 可以回到具体遗器实例及词条。
- 报告同时给出“这套构筑为何适合作为示例”的攻略依据和“每个数值为何成立”的 TBGD / IR 依据，并明确前者不参与 runtime。

### 不允许验收通过

- 在示例中直接写最终生命、攻击、防御、速度、暴击率或伤害答案。
- 用手工状态、手工伤害修正或验证 metadata 冒充光锥 / 套装效果。
- 只展示一张最终面板截图或一条最终伤害，不展示来源贡献和条件反例。
- 六件遗器数值看起来合理，但无法由合法成品 count / step 和当前词条定义重算。
- 为让繁星竞技场生效，在 runtime 中写死 70% 或在示例中提交 `set_active=true`。
- 为让《于夜色中》满档强行使用速度鞋，或者把“满六档”误写成构筑合格的必要条件。
- 以希儿示例通过宣称全光锥、全遗器或全套装完成。

### 最小证据与验证

- P8-S20 source-backed build manifest、成品遗器合法性、assembly ledger、正式场景/provider 注册、condition branches、source walkback 和 replay 验证。
- 复用一次当前指纹下的 focused RuleBook；S18/S19 检查点作为硬前置继承，不重跑其主验证。若纵切暴露 core 缺陷，退回最早责任阶段，不在 S20 顺手修复。
- 默认只写示例 manifest、最终摘要、必要 settlement 抽样和反例矩阵，不写完整 RuleBook 或全量 transition dump。

## 30. P8-S21 全量聚合、回归与文档收口

### 阶段目标

对 P8 的全部阶段、当前 TBGD 装备来源和真实 runtime 做一次统一验收聚合。完成后，P8-DONE 能严格表示“当前已发布光锥和玩家遗器 / 套装 gameplay 机制已经完整接入”，而不是“希儿这一个装备样例能跑”。

### 本阶段只做

- 继承 S0-S20 的当前源码 evidence，验证 source fingerprint、schema version、代码哈希和必需检查非空。
- 生成全光锥、全遗器模板、全主副词条、全套装档位和全 gameplay family 的最终矩阵。
- 要求 lowering / admission / implementation / validation gap 为零，并核对 non-gameplay 证据。
- 在单次 final 中共享一次装备 compilation / RuleBook，并通过生产 runner 集成复核关键负例与 S20 manifest。
- 验证旧字符串式 equipment boundary 不再是接口或完成证据。
- 更新 README、架构文档、DOCUMENTATION_INDEX、CODEX_HANDOFF、AGENTS 和最终 checkpoint。
- 记录 P8 明确不做的 farming、背包、UI 布局和未来版本增量，不将其混入 P8 完成度。

### 本阶段不做

- 不在聚合脚本里补 runtime 逻辑。
- 不引用执行线程外历史 `/tmp` 产物作为唯一证据。
- 不运行与装备没有调用链 / 数据契约关系的全项目无关验证。

### 允许验收通过

- S0-S20 阶段 evidence 全部存在、当前、结构完整，空 checks / 缺 key / 错类型 / 假 `ok` 均被拒绝。
- 全部当前已发布光锥 gameplay ability、玩家遗器模板、词条和套装档位完成闭合，严格 gap 为零。
- 特殊遗器模式和 non-gameplay 节点有逐项来源分类，不被主行正例覆盖。
- 至少抽取一条光锥静态贡献、一条光锥动态 mutation、一条主词条、一条副词条、一条套装静态贡献和一条套装动态 mutation完成全来源反查。
- formal character build、path mismatch、4+2、2+2、非法主词条、非法副词条、unsupported ability 和 stale replay 等关键负例全部仍通过。
- 希儿完整构筑仍通过正式接口运行，且总矩阵明确把它标为端到端 sample，不用它覆盖其他装备行。
- 重验证资源预算和输出规模符合计划，无完整大对象默认落盘。

### 不允许验收通过

- 用手写总表 `gap=0` 覆盖分阶段内部 gap。
- 只统计装备定义数量，不统计 gameplay ability 和真实 transition。
- 将当前无法执行的已发布装备标记为“后续内容扩面”后勾 P8-DONE。
- 把 final 拆成逐阶段主验证重跑，或并行运行多个重聚合压满 IO / 内存。

### 最小证据与验证

- P8-S21 current-source aggregate，默认共享一次 focused equipment compilation / RuleBook build。
- 无 RuleBook 的轻量 preflight 先检查报告、指纹和阶段清单；通过后 final 只运行一次。
- `compileall`、单次 final、`git diff --check`；不单独重跑 S20、P7 聚合或各阶段主验证。
- 重验证使用 `PYTHONDONTWRITEBYTECODE=1 ionice -c3 nice -n 15` 串行运行，输出 `/tmp`，默认只写 summary / matrix / sampled evidence。

## 31. 分层验证与资源预算

P8-S9 至 S21 的详细预算以
`docs/p8_execution_cards/README.md` 第 6 节和当前阶段卡为准。本节只保留总计划级
验收原则，不能被执行线程扩写成第二套命令清单。

### 31.1 唯一默认流程

```text
生产边界拒绝非法状态
  -> 开发期秒级失败切片
  -> 一次阶段主验证
  -> 只对实际修改调用链运行 direct
  -> 阶段职责要求时才运行 catalog/full
```

- 每阶段只有一个主验证入口；`compileall` 和 `git diff --check` 属于 fast，不是第二个业务验证。
- 历史阶段检查点默认继承。未修改调用链时，不因“保险”重跑前序验证器。
- 主验证最多一次诊断和一次最终运行；两次之间只运行失败切片。
- direct 默认最多两个，并必须在报告中写明本次修改如何触达该契约。
- catalog 只在目录、来源、lowering、索引或正式目录准入变化时运行；full 只在 S21 运行。
- 主验证必须由 `/usr/bin/time -v` 计量并由 `timeout` 按单次预算强制终止；超时残留产物不得作为 evidence。

### 31.2 阶段预算

| 阶段 | 累计验证墙钟上限 | 主验证峰值 RSS | 默认总产物 |
|---|---:|---:|---:|
| S9 | 15 分钟 | 1 GiB | 5 MiB |
| S10-S14 | 每阶段 10 分钟 | 768 MiB | 3 MiB |
| S15 | 15 分钟 | 1 GiB | 5 MiB |
| S16-S17 | 每阶段 25 分钟 | 1 GiB | 10 MiB |
| S18-S20 | 每阶段 20 分钟 | 1 GiB | 10 MiB |
| S21 | 45 分钟 | 1.5 GiB | 20 MiB |

达到墙钟、内存或产物任一上限必须停止并重新拆分验证，不能提高限制、并行补跑、
删谓词或把失败改名为 deferred。预算从首次阶段主验证开始累计，必须进入
`ready_for_review` 资源摘要。

预算是止损上限，不是目标。主验证正常设计目标应低于单次上限的一半；诊断运行达到
单次上限的 80% 时，即使业务通过，也必须先缩窄投影、case 或 evidence，再进行最终运行。

### 31.3 构建与证据边界

- 来源、IR/RuleBook、场景和 evidence 过滤必须在各自构建前生效；先完整构建再过滤不算 focused。
- 同一主验证中的来源解析、compiler、RuleBook 和正式场景各最多构建一次并复用。
- validator 只能编排生产入口与独立 oracle，不能复制装配、动作、伤害、事件或 replay。
- 默认不运行 P1-P7 聚合、`validate_v0_209`、旧未过滤/九族聚合，也不写完整 Canonical IR、RuleBook 或 transition。
- S16/S17 各自只验证本阶段 family；S18 不重跑两轨聚合；S20 不重跑 S18/S19；S21 在一个进程内共享一次装备 compilation/RuleBook。
- S9-S15 新验证代码目标不超过 800 行非空 Python，S16-S21 目标不超过 1000 行；超过目标或超过生产改动量时先暂停规划审查。
- 1200 行是未经新执行卡批准不得越过的硬上限，不得通过压缩代码、生成代码或搬入 helper 规避。

## 32. 兼容与迁移口径

- v8 不以旧 v7、旧 model pack、旧 JSON 或旧 UI payload 为兼容目标。
- 当前 `PanelInput` 被大量内核 fixture 使用，不要求一次性删除；但必须明确区分 `kernel_fixture` 与正式 `assembled_character_build`，不能无标记 fallback。
- 工作区内正式角色 scenario 应逐步迁移到构筑输入。若某阶段会改变现有公开 schema，执行卡必须列出所有工作区内调用者和原子迁移方案。
- 旧 `CharacterDataCardIR.card_contract.equipment_boundary` 在 S1 后不得继续充当接口；是否完全删除字段可由 S1 blast radius 决定，但保留兼容文字不得进入 runtime / validation。
- 装备能力接入必须复用现有通用机制。发现底层缺口时应修复通用系统并补直接回归，不能建立第二套 equipment runtime。
- 新版本 TBGD 增加光锥、命途、套装档位、部位模式或 ability 文件时，S0 / S21 应通过数据发现并显式暴露新增 coverage，不因固定枚举静默忽略。S20 示例 manifest 的 source fingerprint 失配时必须重新装配并复核，不允许静默沿用旧最终面板。
