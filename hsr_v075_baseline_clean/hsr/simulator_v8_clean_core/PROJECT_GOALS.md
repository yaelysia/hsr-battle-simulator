# 项目目标与完成定义

## 2026-11-10 方向矫正

项目推进五个月仍看不到终点。用户确认原因是结构性的，而不是执行不够努力：

- 终点被定义为固定来源目录全量，没有任何“到这里就能用”的中间形态，也没有可计量的进度；
- 每个内容的独特行为都必须扩展通用编译器和内核，接入新内容的成本不随积累下降；
- 每个状态变化都要附带可防伪的来源审计，一个功能要付出实现、审计和反例多份成本；
- 这些证明的是执行自洽，而不是与游戏一致；执行速度也无法支撑推演器。

自本日起的四项决定：

1. **终点改为 v1 可用版**：一份用户确定的有限名单，名单内的内容能打、数值与游戏对得上、
   速度够推演器使用。固定目录全量是 v1 之后的扩展方向，不是当前版本的完成条件。
2. **专属行为可以写在内容层**：通用机制表达不了、且只有一个内容使用的行为，写成该内容卡的
   专属处理器；只有多个名单内容共用的行为才扩展通用编译器和内核。
3. **正确性以游戏数值对照衡量**：来源审计降为可开关的调试与测试能力，不再是运行不变量或验收门。
4. **性能是验收项**，与内容接入同步度量，不留到最后。

本文件与其它文档冲突时以本文件和工作区 `AGENTS.md` 为准。2026-11-10 之前的计划、执行说明和
报告按历史记录理解；已验收的实现继续复用，不因矫正而重写。

## 最终目标

建立一个可供人工操作、UI 和外部推演器使用的《崩坏：星穹铁道》战斗模拟器。给定合法战斗配置和
一串外部选择，内核产生与游戏实际战斗一致、确定可重放的战斗结果。

外部推演器像玩家一样控制敌我双方：查询合法动作和目标、选择分支、提交命令并读取结果。
内核负责规则，不实现敌方 AI、自动战斗策略或通关搜索算法。

原生引擎的类、任务拆分、内部回调协议和纯表现组织不属于复刻目标；只有会改变合法操作、目标、
状态、资源、数值或后续触发的语义与顺序需要保留。TBGD 和可靠机制资料（攻略、数据网站、
测试条件明确的实测结论）均可直接作为规则依据。

## v1 完成定义

v1 名单的增减由用户决定（首版于 2026-11-10 由用户委托工程侧选定），写在[工程完结路线](P9_CHARACTER_SHARED_MECHANISM_CLOSURE_TASK_PLAN.md#v1-名单)，
包含角色（及各自要支持的星魂、行迹范围）、光锥与遗器、敌人、关卡环境。名单是唯一的范围权威：
名单外的内容在准入时明确拒绝即可，不是缺陷，也不产生 v1 任务。

名单内每个条目有两项状态，都满足才算完成：

| 状态 | 判定 |
| --- | --- |
| 可战斗 | 从正式构筑入场，该条目在名单范围内的全部战斗分支都能经公开操作执行，并能继续后续合法操作 |
| 数值已对照 | 至少一组记录了版本、构筑、目标与操作的对照：模拟结果与游戏实测或成熟计算器的数值一致 |

v1 整体完成还需要：

- 性能达到下文预算；
- 用户不修改内部状态即可完成配置、双方操作、结算查看、保存与回放，CLI、工作台和外部调用走同一入口；
- 支持范围可查询，且与实际可执行内容一致。

**进度按名单条目计量**：已完成条目数与名单条目数之比就是 v1 进度。局部组件通过、编译通过或
静态闭包通过不计入完成；测试数量、文档数量和审计覆盖不是进度。

### 数值一致

- 伤害、治疗、护盾、削韧、能量等数值默认要求相对误差不超过 1%，或落在游戏显示的取整范围内；
- 行动顺序、目标、触发次数和状态层数必须一致；
- 对照值只用于检验，不能反过来写成规则、修正项或固定答案；
- 容差由用户调整；无法取得对照的条目如实标为“未对照”，不以自洽性证据替代。

### 性能预算

推演器需要大量试算，因此速度是可用性的一部分。初始预算如下，由用户按推演器实际需求调整：

- 规则缓存命中时，建立一场战斗会话不超过 5 秒；
- 普通单条命令的提交平均不超过 0.1 秒；
- 推演器能从已到达的战斗状态继续尝试不同分支，而不必每次从入场重放。

固定一个基准场景持续度量，当前基线与差距记录在[交接](../CODEX_HANDOFF.md)。不通过删除原子提交、
确定性或结算明细来换取速度；为审计服务的证据构造如果是瓶颈，可以改为按需生成。

## 功能范围

v1 名单内纳入会改变以下结果的内容：

- 角色、怪物、召唤物、光锥、遗器和关卡环境的合法战斗构筑；
- 等级、晋阶、行迹、星魂、技能等级和最终装备词条形成的入场状态；
- 双方合法动作、目标、行动窗口和资源约束；
- 伤害、治疗、护盾、韧性、击破、状态、队列、波次、死亡、复活和召唤生命周期；
- 随机选择与可重放 RNG 账本；
- 面向 UI 与推演器的只读查询和命令提交契约。

默认排除，且不随 v1 之后的扩展自动纳入：

- 抽取、掉落、商店、背包和服务端资产管理；
- 角色或装备的材料消耗、强化历史、合成和定向生成；
- 动画、镜头、音效和纯展示逻辑；
- 游戏客户端敌方决策策略、自动配队和自动战斗。

排除项的最终结果若进入战斗，只接收规范化成品，例如最终遗器等级与词条，不复刻其养成过程。

## 架构目标

规则沿以下方向流动：

```text
TBGD / 已采纳机制资料 -> 编译、规则注册或内容专属处理器 -> Canonical IR / 数据卡 IR / RuleBook
         -> 构筑与场景准入 -> 通用战斗内核 -> 查询 / 结算明细 / snapshot / replay
```

- 来源层解释 raw 数据；runtime 不读取 raw、TextMap 或 source trace 决定行为。
- TBGD 首先是参数来源（面板、倍率、韧性、能量、等级表）。原生任务图的编译路径在已经可用的
  内容上继续使用，但不是接入新内容的唯一方式，也不以编译覆盖率衡量进度。
- 内核只处理通用机制，不按名称、固定 ID 或文件名分支；内容专属行为经装配挂载的处理器接入，
  处理器只产生类型化 mutation，数值结算调用内核通用函数。
- 构筑装配把内容定义和玩家输入变成正式入场结果。
- UI 与推演器不自行推算伤害、目标、资源、状态或动作合法性。
- 状态变化经类型化 mutation 原子提交；失败请求不留下部分状态、队列、事件或 RNG 消耗。

分层与处理器边界见 [ARCHITECTURE_BOUNDARY_CONTRACT.md](ARCHITECTURE_BOUNDARY_CONTRACT.md)，
永久红线见 [FORBIDDEN.md](FORBIDDEN.md)。

## 正确性目标

1. **与游戏一致**：按上文“数值一致”对照。这是内容是否正确的唯一判据。
2. **确定可重放**：同一初始状态、命令序列和 RNG 输入得到同一合法性判定、目标集合、
   mutation 与 RNG 消费顺序、最终状态和胜负。
3. **不猜**：规则未知或依据不足时拒绝执行并说明原因，不用经验值、默认行为或固定答案补齐。

确定性 replay 验证执行自洽，游戏对照验证规则正确，两者不能互相替代。来源可查的要求是：
规则和处理器在定义处注明实际依据及适用条件；不要求每个 mutation 在运行时反查到来源节点，
也不为审计证据的缺失、替换或篡改另建防伪检查。

## v1 之后

固定目录内其余角色、怪物、关卡与模式按用户后续确定的名单分批扩展，每批沿用同一完成定义。
来源版本升级、新产品目标和大规模重构另行决定，不自动并入当前版本。

## 质量优先级

```text
v1 可用 > 与游戏一致 > 推演性能 > 内核简洁 > 来源可查 > 目录覆盖 > 旧版兼容
```

旧 v7 和旧 model pack 只可帮助定位历史意图和做数值对照，不能补规则或约束 v8 架构。
当前进度只在 [`../CODEX_HANDOFF.md`](../CODEX_HANDOFF.md) 维护，不写入本文件。
